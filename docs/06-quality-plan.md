# 품질 계획

## 배포 게이트

1. `npm run lint`
2. `npm run build`
3. 핵심 사용자 흐름 수동 검증
4. Firebase Rules 권한 검증
5. 모바일·데스크톱 반응형 확인
6. 변경 문서와 릴리스 기록 확인

## 핵심 시나리오

- 비로그인 탐색·검색·상세 조회
- 회원가입·로그인·로그아웃
- 찜·폴더·메모 생성과 삭제
- AI 일정 정상 생성·빈 입력·실패·재시도
- 게시글·댓글 작성·수정·삭제·좋아요
- 다른 사용자의 데이터 접근 거부
- 공공 API 장애·빈 결과·캐시 만료
- AI timeout
- AI HTTP 429(rate limit)
- AI 잘못된 JSON 응답
- AI 재생성 한도 초과

## 측정

초기 로딩 시간, 주요 API 응답 시간, 캐시 적중률, 오류율, AI 생성 성공률을 릴리스별 기록합니다. 자동 테스트 도입 시 핵심 API/상태 로직부터 시작하고, 브라우저 E2E는 대표 흐름에 한정합니다. AI 배포 게이트는 정상 생성뿐 아니라 timeout, HTTP 429, 잘못된 JSON, 재생성 한도 초과의 사용자 안내와 로그 결과까지 확인합니다.

## 성능 최적화 검증

Vite 빌드에서 500kB 초과 청크 경고가 발생하는 경우 이를 기술 부채로 분류합니다. 해결은 계획, 구현, 측정, 증빙의 순서로 진행합니다.

- 적용 전 `npm run build` 결과에서 주요 청크 파일명과 gzip 전후 크기를 기록합니다.
- 1차 개선은 `src/main.jsx`의 라우트 단위 코드 스플리팅으로 진행합니다.
- 2차 개선은 측정 결과를 근거로 `vite.config.js`의 `manualChunks` 적용 여부를 결정합니다.
- 완료 판단은 경고 제거 여부만으로 하지 않고, 초기 로딩 청크 크기와 주요 화면 진입 시 추가 청크 크기 비교로 판단합니다.
- 측정값이 없는 상태에서는 “코드 스플리팅 계획 수립” 또는 “개선 후보 정의”로만 표현합니다.

## 성능 측정 데이터 원칙

성능 데이터는 MVP 단계에서 원시 로그를 장기간 누적하기보다 릴리스별 집계 지표를 우선합니다. 사용자별 `performanceLogs`를 무제한 저장하는 구조는 개인정보, 저장 비용, Rules 관리 부담이 있으므로 기본값으로 채택하지 않습니다.

- 초기 기준선은 Lighthouse, 브라우저 Performance 패널, `npm run build` 로그로 확보합니다.
- API 캐시 상태는 현재 개발 모드의 `ApiCacheStatus` 패널과 `codetrip:api-cache-status` 이벤트를 개발·시연 세션의 디버깅 증빙으로만 사용합니다.
- 캐시 적중률을 성과로 주장하려면 개발·시연 세션 단위로 fresh hit(memory, local, remote), network, stale fallback 이벤트 수를 별도 집계해야 합니다.
- 운영 집계 경로를 도입하는 경우 구현 위치, 수집 조건, 보존 기간, Firebase Rules 적용 범위를 함께 문서화합니다.
- AI 성공률은 Gemini 호출 성공·실패·timeout·429·JSON 파싱 실패·재생성 한도 초과를 구분해 기록할 때만 정량 지표로 사용합니다.
