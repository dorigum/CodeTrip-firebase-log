# CodeTrip NotebookLM 분석 규칙

앞으로 CodeTrip 프로젝트 문서를 분석할 때는 아래 규칙을 반드시 따른다.

## 1. 계획과 실제 상태를 구분한다

문서에 작성된 목표, WBS, 품질 기준, KPI는 “계획” 또는 “평가 기준”으로 분류한다.

실제 코드, 커밋 기록, 테스트 결과, 배포 기록, 측정 로그로 확인되지 않은 항목은 “완료” 또는 “달성”으로 표현하지 않는다.

예:
- “AI 생성 성공률을 측정해야 한다”는 계획이다.
- 실제 성공/실패 로그가 없으면 “AI 생성 성공률이 확보되었다”고 말하지 않는다.

## 2. 수치 표현은 증빙이 있을 때만 사용한다

100%, 완료율, 성공률, 오류율, 응답 시간, 캐시 적중률 등 정량 수치는 반드시 근거 문서나 측정 결과가 있을 때만 사용한다.

근거가 없으면 다음처럼 표현한다.

- “측정 기준은 정의되어 있음”
- “현재 측정값은 미확인”
- “추후 릴리스별 기록 필요”
- “정량 성과로 주장하기에는 증빙 부족”

## 3. 문서 유형을 구분한다

CodeTrip 문서는 다음 유형으로 구분해서 해석한다.

- 프로젝트 헌장: 목적, 범위, 성공 기준
- 요구사항 문서: 기능 요구사항과 우선순위
- 사용자 흐름 문서: 예상 사용자 여정
- 아키텍처 문서: 설계 기준과 기술 구조
- 데이터·보안 문서: 권한, 데이터 모델, 보안 기준
- 품질 문서: 테스트 계획과 검증 기준
- WBS 문서: 일정 계획과 작업 분해
- 운영 문서: 배포, 장애 대응, 릴리스 기준
- 지표 문서: KPI 정의와 측정 계약
- AI 하네스 문서: Gemini API 입력, 검증, 실패 처리 기준

문서가 “계획 문서”인지 “실제 결과 문서”인지 구분해서 설명한다.

## 4. 완료 판단 기준

어떤 항목을 완료로 판단하려면 최소 하나 이상의 증빙이 필요하다.

- 실제 코드 구현 위치
- 커밋 또는 PR 기록
- 테스트 결과
- 빌드 결과
- 배포 기록
- 측정 로그
- 스크린샷 또는 시연 기록
- 명시적인 완료 체크리스트

증빙이 없으면 “완료”가 아니라 “정의됨”, “계획됨”, “기준 수립됨”으로 표현한다.

## 5. 추천 표현

증빙이 있는 경우:
- “구현되어 있음”
- “문서와 코드가 일치함”
- “빌드 결과로 검증됨”
- “배포 기록으로 확인됨”

증빙이 부족한 경우:
- “기준은 정의되어 있으나 측정값은 없음”
- “계획은 수립되어 있으나 실행 기록은 부족함”
- “문서상 요구사항이며 실제 완료 여부는 추가 확인 필요”
- “MVP 목표로 설정되어 있음”

피해야 할 표현:
- “100% 완료”
- “완전히 검증됨”
- “운영 준비 완료”
- “성능이 확보됨”
- “보안이 보장됨”
- “KPI가 달성됨”

위 표현은 실제 증빙이 있을 때만 사용한다.

## 6. 답변 형식

CodeTrip을 분석할 때는 가능하면 아래 형식을 사용한다.

| 항목  | 문서상 상태 | 실제 확인 상태 | 증빙  | 추가 필요 작업 |
| --- | ------ | -------- | --- | -------- |

예:

| 항목 | 문서상 상태 | 실제 확인 상태 | 증빙 | 추가 필요 작업 |
|---|---|---|---|---|
| AI 생성 성공률 | 측정 지표로 정의됨 | 실제 측정값 미확인 | docs/09-metrics.md | 성공/실패 로그 수집 필요 |

## 7. 최종 평가 방식

CodeTrip의 현재 상태를 평가할 때는 다음처럼 나누어 말한다.

- 문서 구조화 수준
- 구현 완성도
- 검증 수준
- 운영 준비도
- 포트폴리오/심사 설명 가능성

각 항목은 근거가 있는 경우에만 정량 평가하고, 근거가 부족하면 정성 평가로 제한한다.

## 8. 우선순위 규칙

문서 내용이 서로 충돌할 경우 최신 커밋의 `docs/` 문서를 우선한다. NotebookLM 요약, AI 채팅 응답, 자동 생성 분석은 원문 문서와 실제 증빙보다 낮은 신뢰도로 취급한다.
