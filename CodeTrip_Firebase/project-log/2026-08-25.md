# 2026-08-25 작업 로그

> 이 문서는 PR #28 `feature/trip-date-planning` 브랜치에서 AI 플래너 폴더 주소 보강 경합 처리, Info 화면 버전 표기, 모바일 하단 내비게이션 보강, 개발용 캐시 패널 위치 조정 작업을 기록합니다.

## 1. 작업 개요

AI 여행 일정 날짜 기능을 추가한 이후, 폴더 기반 생성 흐름에서 비동기 주소 보강이 끝나기 전에 사용자가 생성 버튼을 누르거나 입력값을 변경할 수 있는 경로를 보완했습니다. 이번 작업의 목적은 폴더 선택, 장소 주소 보강, 지역명 자동 반영, 생성 요청이 서로 충돌하지 않도록 AI Planner의 busy-state와 최신성 검증을 더 명확하게 만드는 것입니다.

또한 제출 직전 MVP 후보 상태를 더 정확하게 드러내기 위해 Info 화면 버전 표기를 `MVP 0.9.0-rc`로 조정했습니다. 모바일 사용성 측면에서는 하단 내비게이션에 `Info` 진입점을 추가하고, `My Page`는 사용자 관점에서 가장 찾기 쉬운 오른쪽 끝에 유지하도록 정리했습니다. `Info` 메뉴는 데스크톱과 동일하게 외부 참고 링크와 About 화면으로 이어지는 하위 메뉴를 모바일 팝업으로 제공합니다.

## 2. AI Planner 폴더 주소 보강 상태 처리

폴더 기반 AI 일정 생성 모드에서는 선택한 폴더 안의 여행지 주소가 부족한 경우 `hydratePlaceAddresses()`가 비동기로 주소를 보강합니다. 이 작업이 진행 중일 때 생성 버튼이 활성화되어 있으면, 화면에는 아직 보강 중인 데이터가 표시되고 있는데 생성 요청은 이전 상태를 기준으로 실행될 수 있습니다.

이를 보완하기 위해 `folderHydrating` 상태를 추가했습니다.

- 폴더 장소 주소 보강 시작 시 `folderHydrating`을 `true`로 설정합니다.
- `plannerBusy` 조건에 `generating`, `saving`, `folderHydrating`을 함께 포함합니다.
- 생성 또는 저장 중이 아닌 경우에만 폴더 변경을 허용하도록 `plannerActionBusy`를 분리했습니다.
- 주소 보강 결과는 `folderSelectionRequestRef`와 `plannerRevisionRef`가 모두 최신일 때만 화면 상태에 반영합니다.
- 주소 보강 실패 시에는 기존 폴더 장소 목록을 fallback으로 사용하고, 사용자가 생성 흐름을 이어갈 수 있도록 했습니다.

이 변경으로 폴더 선택 직후 주소 보강이 진행되는 짧은 구간에서 중복 생성, 오래된 폴더 결과 반영, 지역명 덮어쓰기 가능성을 줄였습니다.

## 4. 모바일 하단 내비게이션 Info 진입점 추가

모바일 웹 화면에서는 하단 탭 영역에 `Info` 메뉴가 노출되지 않아 정보 화면 접근성이 떨어지는 문제가 있었습니다. 사용자 관점에서는 개인 계정과 저장 데이터를 확인하는 `My Page`가 가장 오른쪽에 고정되는 편이 더 자연스럽기 때문에, 모바일 하단 내비게이션 순서를 아래처럼 정리했습니다.

1. Home
2. Explore
3. Festivals
4. AI Planner
5. Board
6. Info
7. My Page

이 구조는 `My Page`를 오른쪽 끝에 유지하면서도, 서비스 정보와 시스템 안내 화면에 모바일에서도 접근할 수 있게 합니다.

`Info` 탭은 단순히 `/info`로 바로 이동하는 링크가 아니라, `My Page`와 같은 방식의 모바일 하위 메뉴 팝업을 띄우도록 수정했습니다. 모바일 팝업에서는 공공 와이파이, 세이프스테이, 교통 예약 링크와 About CodeTrip 화면으로 이동할 수 있습니다. 다른 하단 메뉴를 누르면 `Info` 팝업과 `My Page` 팝업이 서로 닫히도록 처리했습니다.

## 5. Info 전용 개발용 API 캐시 패널 위치 조정

개발 모드에서 표시되는 `API_CACHE.LOG` 패널이 화면 폭을 줄였을 때 왼쪽 사이드바 또는 메뉴 항목과 겹치는 문제가 있었습니다. 이 패널은 사용자 기능이 아니라 개발·검증용 보조 UI이므로, Info 화면에서만 표시되도록 제한하고 주요 내비게이션과 충돌하지 않도록 오른쪽 하단 기준으로 위치를 조정했습니다.

이 변경은 API 캐시 상태를 확인하는 기능 자체를 바꾸지 않고, 일반 탐색·축제·AI Planner 화면의 콘텐츠를 가리지 않도록 표시 범위를 줄이는 UI 안정화 작업입니다.

## 9. TourAPI 신규 여행지 알림 구조 추가

AWS/Express 환경에서 사용하던 한국관광공사 신규 여행지 알림 아이디어를 현재 Firebase 구조에서도 적용할 수 있는지 검토하고, Firebase 기반 MVP 구현을 추가했습니다.

이번 구현은 사용자별 알림을 대량 생성하는 방식이 아니라, 서버 배치가 공용 신규 여행지 피드를 저장하고 Header 알림 UI가 기존 개인 알림과 함께 표시하는 방식입니다. 이 구조는 사용자 수가 늘어도 Realtime Database 쓰기량이 급격히 증가하지 않아 비용과 운영 안정성 측면에서 더 적합합니다.

### 9.1 Functions 구조

- `functions/index.js`에 `syncTourApiUpdates` Scheduled Function을 추가했습니다.
- 함수는 하루 1회 `KorService2.areaBasedList2`를 조회합니다.
- 최신 30개 항목을 확인하고, 기존에 저장되지 않은 `contentId`만 신규 여행지로 저장합니다.
- 신규 여행지는 `tourApiUpdates/items/{contentId}`에 저장합니다.
- 저장된 업데이트 피드는 최근 100개까지만 유지하도록 정리 기준을 추가했습니다.
- TourAPI 인증키는 `TOUR_API_SERVICE_KEY` Functions Secret으로 관리하도록 설계했습니다.

### 9.2 알림 UI 연동

- `src/api/notificationApi.js`에서 기존 `users/{uid}/notifications` 알림과 `tourApiUpdates/items` 공용 신규 여행지 알림을 병합합니다.
- 신규 여행지 알림은 `[신규 여행지] {title}` 형식의 메시지로 표시합니다.
- 사용자가 알림을 클릭하면 `/explore/{contentId}` 상세 화면으로 이동합니다.
- 읽음, 개별 숨김, 읽은 알림 삭제 상태는 `users/{uid}/tourApiUpdateReads/{contentId}`에 저장합니다.
- 공용 업데이트 피드를 사용자별로 복제하지 않고, 사용자별 상태만 분리해 저장합니다.

### 9.3 데이터·보안 규칙

- `database.rules.json`에 `tourApiUpdates` 읽기 규칙을 추가했습니다.
- `tourApiUpdates` 클라이언트 쓰기는 차단했습니다.
- `users/{uid}/tourApiUpdateReads`는 본인 경로에서만 읽음·숨김 상태를 저장할 수 있도록 기존 `users/{uid}` 권한 경계 안에 배치했습니다.

## 10. TourAPI 신규 여행지 알림 CodeRabbit 피드백 반영

PR #29에서 확인된 TourAPI 신규 여행지 알림 관련 피드백을 반영했습니다.

### 10.1 반영 내용

- `syncTourApiUpdates`의 TourAPI 조회 정렬 기준을 이미지 포함 등록일 최신순으로 변경했습니다.
  - 기존 `arrange=O`는 신규 등록 감지 목적에 적합하지 않을 수 있어 `arrange=R`로 조정했습니다.
- TourAPI 응답 검증을 강화했습니다.
  - `response.header.resultCode`가 `0000`이 아닌 경우 동기화 실패로 처리합니다.
  - `response.body.items.item` 구조가 없으면 성공한 빈 결과로 기록하지 않고 오류로 처리합니다.
- Header 알림 병합 로직에서 TourAPI 신규 여행지 알림의 숨김 필터 순서를 조정했습니다.
  - 숨김 상태를 먼저 제거한 뒤 표시 개수 제한을 적용하도록 변경했습니다.
- `docs/39-tourapi-update-notification-plan.md`에 신규 알림 동기화 경로의 Secret 기준, 응답 검증 기준, 등록일 최신순 조회 기준을 보강했습니다.

## 12. 프로필·게시글 이미지 Firebase Storage 업로드 전환

프로필 이미지 입력을 URL 또는 base64 data URL에 의존하던 구조를 Firebase Storage 업로드 후 다운로드 URL을 저장하는 구조로 전환했습니다. 같은 방식으로 게시글 작성 화면에서도 로컬 이미지 파일을 업로드해 Markdown 이미지 링크로 삽입할 수 있도록 확장했습니다.

### 12.1 배경

- 프로필 수정 화면에서 데스크톱 이미지 파일을 선택하면 기존 `authApi.uploadImage()`가 파일을 base64 data URL로 변환했습니다.
- base64 data URL은 길이가 매우 길어 Firebase Authentication `photoURL` 제한을 초과할 수 있고, 실제 프로필 저장 시 `auth/invalid-profile-attribute` 오류가 발생했습니다.
- 게시글 작성 화면은 이미지 URL 직접 입력 중심이라 로컬 파일 첨부가 어렵고, 긴 data URL을 본문에 넣는 방식은 문서 크기와 렌더링 안정성 측면에서 적합하지 않았습니다.

### 12.2 변경 내용

- `src/firebase.js`
  - Firebase Storage 인스턴스를 초기화하고 `firebaseStorage`로 export했습니다.
- `src/api/storageApi.js`
  - 공통 이미지 업로드 API를 추가했습니다.
  - 인증 사용자 확인, 이미지 타입 검증, 1MB 초과 이미지 클라이언트 압축, 파일명 정규화, Storage 업로드, 다운로드 URL 반환을 담당합니다.
  - 프로필 이미지는 `users/{uid}/profile`, 게시글 이미지는 `users/{uid}/board` 경로에 저장합니다.
- `src/api/authApi.js`
  - 프로필 이미지 업로드를 FileReader data URL 변환에서 Firebase Storage 업로드로 변경했습니다.
  - 프로필 저장 시에는 짧은 다운로드 URL을 `photoURL`과 사용자 프로필 데이터에 저장합니다.
- `src/pages/Settings.jsx`
  - 프로필 이미지 업로드 안내 문구를 Storage 업로드 기준으로 변경했습니다.
  - 사용자는 파일 업로드 또는 외부 이미지 URL 입력을 선택할 수 있습니다.
- `src/components/MarkdownEditor.jsx`, `src/pages/BoardWrite.jsx`
  - Markdown 에디터에 이미지 파일 업로드 버튼을 추가했습니다.
  - 게시글 작성 중 파일을 선택하면 Storage에 업로드하고, 반환된 다운로드 URL을 `![이미지명](URL)` 형식으로 본문에 삽입합니다.
- `firebase.json`, `storage.rules`
  - Firebase Storage Rules 배포 대상을 추가했습니다.
  - Storage Rules는 `users/{uid}/profile`과 `users/{uid}/board` 하위 경로에서 인증된 동일 UID만 이미지 파일을 쓸 수 있도록 제한합니다.

### 12.3 보안 기준

- 이미지 원본 또는 base64 data URL을 Realtime Database에 저장하지 않습니다.
- Storage 쓰기는 인증된 사용자 본인의 UID 경로로 제한합니다.
- 허용 폴더는 `profile`, `board`로 제한합니다.
- 업로드 파일은 이미지 MIME 타입이어야 하며, Rules 기준 2MB 미만이어야 합니다.
- 프로필과 게시글 이미지는 화면 렌더링을 위해 다운로드 URL을 공개 읽기 가능한 자원으로 취급합니다.

### 12.4 검증 결과

- `npm run lint`
  - 통과했습니다.
  - 기존 React Hook warning 11개는 유지됐습니다.
- `npm run build`
  - 통과했습니다.
  - 기존 Vite 500kB 초과 청크 경고는 유지됐습니다.
- Storage Rules 배포 후 수동 확인
  - 프로필 수정 화면에서 로컬 이미지 파일을 업로드하고 저장합니다.
  - 저장 후 Header, SideBar, 마이페이지 프로필 이미지가 Storage 다운로드 URL 기준으로 표시되는지 확인합니다.
  - 게시글 작성 화면에서 이미지 파일을 첨부하고 Markdown 본문에 이미지 링크가 삽입되는지 확인합니다.
  - 게시글 상세 화면에서 첨부 이미지가 정상 표시되는지 확인합니다.

### 12.5 후속 작업

- Hosting 재배포 후 배포 사이트에서 프로필 이미지 업로드와 게시글 이미지 업로드를 수동 검증합니다.
- 필요하면 게시글 이미지 업로드 파일 크기 제한과 압축 품질을 별도 UX 메시지로 세분화합니다.

### 12.6 프로필 이미지 저장 경로 보정

- 프로필 이미지를 변경할 때마다 `users/{uid}/profile/{timestamp}-파일명` 경로에 새 파일이 누적 저장되는 구조를 확인했습니다.
- 프로필 이미지는 사용자가 현재 사진 1개만 필요로 하는 성격이 강하므로, 불필요한 Storage 파일 누적을 줄이기 위해 고정 경로 덮어쓰기 방식으로 변경했습니다.
- 변경 후 프로필 이미지는 `users/{uid}/profile/avatar` 경로에 업로드됩니다.
- 같은 Storage 객체를 덮어쓰면 다운로드 URL이 같아 브라우저가 이전 이미지를 캐시할 수 있으므로, 프로필 저장 URL에는 `v={uploadedAt}` 쿼리 파라미터를 붙여 최신 이미지 표시를 유도합니다.
- 게시글 이미지는 게시글 본문 Markdown이 과거 이미지 URL을 계속 참조할 수 있으므로 기존처럼 `users/{uid}/board/{timestamp}-파일명` 누적 저장 방식을 유지합니다.

## 13. PR #29 CodeRabbit 추가 피드백 반영

Firebase Storage 생성과 배포 이후 CodeRabbit이 남긴 추가 피드백을 반영했습니다. 이번 수정은 TourAPI 신규 여행지 동기화의 정상 빈 응답 처리, Storage 이미지 압축 기준, TourAPI 알림 일괄 처리 범위, Firebase 배포 가이드 정합성을 보강하는 작업입니다.

### 13.1 TourAPI 정상 빈 응답 처리

- `syncTourApiUpdates`에서 사용하는 TourAPI 응답 파싱 로직을 `functions/tourApiUpdates.js`로 분리했습니다.
- 한국관광공사 TourAPI가 `resultCode: "0000"`, `totalCount: "0"`, `items: ""` 형태로 정상 빈 결과를 반환하는 경우 동기화 실패가 아닌 빈 배열로 처리하도록 수정했습니다.
- `totalCount`가 0이 아닌데 `items.item` 구조가 없으면 기존처럼 응답 구조 오류로 분류합니다.
- `functions/test/tourApiUpdates.test.js`를 추가해 정상 빈 응답, 비정상 누락 구조, 단일 item 정규화 fixture를 검증합니다.

### 13.2 Storage 이미지 압축 기준 보강

- 기존에는 파일 크기가 1MB 이하이면 이미지 해상도를 확인하지 않고 그대로 반환했습니다.

- 파일 용량이 1MB 이하더라도 가로 또는 세로가 1920px을 초과하면 1920px 이하로 리사이즈한 뒤 업로드합니다.
- 파일 용량과 해상도가 모두 기준 이하면 원본 파일을 유지합니다.

### 13.3 TourAPI 알림 일괄 처리 범위 보정

- `markAllRead()`와 `deleteReadNotifications()`는 표시 제한 10개에 묶이지 않고 숨김 처리되지 않은 전체 TourAPI 신규 여행지 알림을 대상으로 처리하도록 분리했습니다.

## 14. PR #29 CodeRabbit 추가 피드백 2차 반영

CodeRabbit이 추가로 남긴 Storage 이미지 압축 실패 처리와 TourAPI 알림 일괄 삭제 범위 피드백을 확인하고 반영했습니다. 이번 수정은 사용자가 업로드하는 이미지가 검증 기준을 우회하지 못하게 하고, 읽은 TourAPI 알림 삭제가 화면에 표시된 최신 10개에만 제한되지 않도록 하는 안정성 보완 작업입니다.

### 14.1 Storage 이미지 압축 실패 시 업로드 차단

- 기존 압축 로직은 Canvas context 생성 실패, `toBlob()` 실패, 이미지 로드 실패 상황에서 원본 파일을 그대로 반환할 수 있었습니다.
- 이 경우 원본 파일이 1MB를 초과하거나 1920px 제한을 초과해도 업로드까지 이어질 가능성이 있었습니다.
- 변경 후에는 다음 상황을 업로드 실패로 처리합니다.
  - 브라우저가 이미지 파일을 읽지 못하는 경우
  - Canvas context를 생성하지 못하는 경우
  - JPEG Blob 생성에 실패하는 경우
  - 압축 품질을 낮춰도 1MB 이하로 줄어들지 않는 경우
- 따라서 `uploadBytes()`로 전달되는 파일은 원본 유지 조건을 만족하거나, 압축 결과가 1MB 이하인 경우로 제한됩니다.

### 14.2 읽은 TourAPI 알림 삭제 범위 보정

- `deleteReadNotifications()`가 표시용 기본 제한인 최신 10개 TourAPI 알림만 조회하는 문제를 확인했습니다.
- 변경 후에는 `getTourApiUpdateNotifications(user.id, { limit: null })`을 사용해 숨김 처리되지 않은 전체 TourAPI 알림을 대상으로 읽은 알림 숨김 처리를 수행합니다.
- `markAllRead()`와 동일한 범위 기준을 사용하므로, 11번째 이후의 읽은 TourAPI 알림도 “읽은 알림 삭제” 동작에서 누락되지 않습니다.

### 14.3 검증 결과

- `npm run lint`
  - 통과했습니다.
  - 기존 React Hook warning 11개는 유지됐습니다.
- `npm run build`
  - 통과했습니다.
  - sandbox 권한 제한으로 최초 실행 시 Vite 임시 파일 생성 오류가 발생했으나, 권한 상승 재실행 후 production build가 정상 완료됐습니다.
