## 1. CodeRabbit 리뷰: 댓글 인덱스 참조 무결성 검증

### 문제

`boardCommentsByPost/{postId}/{commentId}`와 `travelCommentsByContent/{contentId}/{commentId}`는 작성자 UID만으로 생성될 수 있어, 사용자가 다른 작성자의 댓글을 가리키거나 실제 댓글의 게시글·여행지 ID와 다른 인덱스를 만들 수 있었습니다.

### 처리

- 인덱스 생성·수정 시 다중 경로 업데이트가 완료된 뒤의 `boardComments`·`travelComments` 원본 댓글을 참조하도록 Rules를 보강했습니다.
- 원본 댓글의 `user_id`가 인증 사용자와 같고, `post_id` 또는 `content_id`, `comment_id`가 인덱스 경로와 일치할 때만 허용합니다.
- 기존 인덱스 삭제는 인덱스 작성자만 허용하고, 게시글 삭제 시 게시글 작성자가 인덱스 전체를 정리하는 기존 흐름은 유지했습니다.
- Emulator 회귀 테스트에 정상 다중 경로 생성과 타인 댓글 참조·다른 콘텐츠 ID 참조 위조 거부를 각각 추가했습니다.

### 확인 기준

- 댓글과 인덱스를 하나의 `update()`로 생성할 수 있어야 합니다.
- 타인의 기존 댓글을 인덱스에 연결하거나, 자신의 댓글을 다른 게시글·여행지 인덱스에 연결하려는 요청은 거부되어야 합니다.

## 2. CodeRabbit 리뷰: 선택된 콘텐츠만 좋아요 조회

### 문제

게시글·댓글 목록과 마이페이지 활동 목록은 필요한 ID가 있어도 `likes/boardPosts`, `likes/boardComments`, `likes/travelComments` 전체를 읽었습니다. 좋아요 데이터가 누적될수록 네트워크 전송·파싱 비용이 증가할 수 있었습니다.

### 처리

- `getLikesByIds()` 공용 헬퍼를 추가해 화면에 표시할 콘텐츠 ID의 좋아요 맵만 병렬로 읽도록 변경했습니다.
- 게시글 목록·선택 게시글 목록, 게시글 댓글·여행지 댓글 목록, 마이페이지의 작성 댓글·여행지 댓글 목록에 적용했습니다.
- 단일 게시글 상세 및 좋아요 토글 후 개수 조회는 이미 해당 콘텐츠 ID 하나만 읽으므로 기존 방식을 유지했습니다.

### 확인 기준

- 목록·활동 화면은 선택된 콘텐츠의 좋아요 상태·개수를 기존과 동일하게 표시해야 합니다.
- 각 목록 조회에서 전체 `likes/{유형}` 루트가 아니라 `likes/{유형}/{ID}`만 요청해야 합니다.

## 4. 축제 상세 소개 가독성 및 링크 이동 개선

### 문제

축제 상세의 `overview`와 `detail_info`는 TourAPI가 제공한 긴 소개 문장을 그대로 HTML로 출력했습니다. 운영 시간·장소·참여 방법 같은 핵심 정보를 한 번에 찾기 어렵고, 본문에 포함된 URL도 클릭해 이동할 수 없었습니다.

### 처리

- 축제(`contenttypeid: 15`)의 소개 문장을 `축제 설명`, `운영 시간`, `장소`, `참여 방법`, `추가 안내`로 분류해 문단과 제목을 나눠 표시합니다.
- 소개·상세 정보의 `http`·`https` URL을 새 탭에서 열리는 텍스트 링크로 렌더링합니다.
- 외부 API HTML을 `dangerouslySetInnerHTML`로 직접 출력하던 방식을 텍스트 기반 렌더링으로 바꿔, 소개·상세 정보의 임의 HTML이 화면에 주입되지 않도록 했습니다.

### 확인 기준

- 축제 소개에서 운영 시간·장소·참여 방법이 독립된 문단으로 표시되어야 합니다.
- 본문의 URL을 선택하면 해당 주소가 새 탭에서 열려야 합니다.
- 축제가 아닌 여행지 상세와 URL이 없는 상세 정보도 기존 텍스트가 정상 표시되어야 합니다.

## 6. 축제 정보 카드 공백 및 본문 URL 링크 범위 보정

### 문제

축제 정보 카드가 홀수 개면 2열 그리드의 마지막 오른쪽 셀이 회색 공백으로 남았습니다. 또한 본문 URL 추출이 공백 전까지의 모든 문자를 링크로 포함해 URL 뒤 조사·괄호가 붙은 경우 잘못된 주소가 열렸습니다.

### 처리

- 축제 정보 카드가 홀수 개일 때 마지막 항목이 데스크톱 2열 전체를 차지하도록 병합했습니다.
- URL 패턴을 표준 URL 문자로 한정하고, 끝의 문장 부호·괄호는 링크 밖 텍스트로 유지하도록 보정했습니다.

### 확인 기준

- 홈페이지 항목처럼 마지막 카드가 하나만 남으면 공백 없이 한 줄 전체에 표시되어야 합니다.
- `https://ddp.or.kr/?menuno=797)를` 같은 문장에서 링크는 `https://ddp.or.kr/?menuno=797`까지만 포함하고, 뒤의 `)를`은 일반 텍스트로 남아야 합니다.

## 7. 축제 소개 중복 제거 및 공식 홈페이지 링크 보완

### 문제

TourAPI의 `overview`와 `detail_info`에 모두 `행사소개`가 있으면 상단 축제 설명과 하단 행사소개가 같은 내용을 반복했습니다. 또한 공식 홈페이지 값이 `공식 홈페이지 https://...`처럼 설명 문구와 URL을 함께 제공하면 전체 문자열이 URL로 시작하지 않아 홈페이지 카드 링크가 만들어지지 않았습니다.

### 처리

- 하단 상세 정보에 `행사소개` 또는 `축제소개`가 있으면 상단 소개의 `축제 설명` 문단만 숨기고, 상단의 운영·장소·참여 안내는 유지합니다.
- 홈페이지 값에서 HTML `href`뿐 아니라 본문에 포함된 첫 `http`·`https` URL도 추출해 공식 홈페이지 카드에 연결했습니다.
- 하단 상세 정보의 줄 간격을 상단 행사 정보와 동일한 `leading-loose`로 맞췄습니다.

### 확인 기준

- 하단 행사소개가 있을 때 같은 설명이 상단에 다시 표시되지 않아야 합니다.
- `공식 홈페이지 https://www.ntok.go.kr/...` 형식도 공식 홈페이지 카드에서 새 탭 링크로 열려야 합니다.
- 하단 행사소개·행사내용의 줄 간격이 상단 정보와 일관되게 보여야 합니다.

## 8. 하단 행사소개가 있는 축제의 상단 요약 유지

### 문제

하단 `행사소개`가 있을 때 상단의 중복 설명을 모두 제외하자, 일부 축제는 맥락 없는 `추가 안내`만 상단에 남아 카드 구성이 어색해 보였습니다.

### 처리

- 하단 행사소개가 있는 경우에도 상단 `축제 설명`을 유지합니다.
- 상단 설명은 원본 소개의 첫 두 문장, 최대 260자로 요약해 축제의 맥락만 빠르게 파악할 수 있게 했습니다.
- 하단 상세 정보는 기존처럼 전체 행사소개·행사내용을 제공하므로 상세 내용의 중복 노출은 줄였습니다.

### 확인 기준

- 상단에는 `추가 안내`만 단독으로 남지 않고 `축제 설명` 요약이 표시되어야 합니다.
- 하단 행사소개에는 상세 원문이 유지되어야 합니다.

## 9. 여행지 목록 카드 UI 및 반응형 페이지 수 통일

### 문제

여행지 탐색 카드는 행사 카드와 달리 별도의 강조 버튼(`상세보기`)과 고정 높이 이미지를 사용해 화면 크기에 따라 버튼이 눌리거나 카드 균형이 무너져 보였습니다. 또한 3열 레이아웃에서 한 페이지에 10개를 불러와 마지막 줄에 카드 하나만 남았습니다.

### 처리

- 여행지 카드를 행사 카드와 같은 이미지 비율, 제목·주소 메타, 하단 `EXPLORE →` 링크 구조로 통일했습니다.
- 위시리스트는 카드 우측 상단 아이콘 버튼으로 이동해 상세 이동 링크와 독립적으로 동작합니다.
- 여행지 목록 페이지 수를 4열 이상 12개, 3열 9개, 2열 6개로 조정해 각 화면 폭에서 마지막 줄의 빈 카드 영역을 없앴습니다.

### 확인 기준

- 여행지·행사 카드는 동일한 하단 `EXPLORE →` 탐색 패턴과 균일한 이미지 비율로 표시되어야 합니다.
- 좁은 데스크톱 3열에서는 9개, 넓은 화면 4열에서는 12개가 표시되어 마지막 줄이 비지 않아야 합니다.
- 위시리스트 추가·해제와 상세 페이지 이동이 각각 정상 동작해야 합니다.

## 10. 축제 상세 외부 링크 분리 및 아이콘 표시

### 문제

TourAPI의 홈페이지 필드에는 공식 홈페이지와 Instagram 등 여러 외부 URL이 하나의 문자열로 함께 제공될 수 있습니다. 기존에는 전체 문자열을 하나의 링크로 렌더링해 URL이 붙어 보이고 올바른 주소로 이동하기 어려웠습니다.

### 처리

- 홈페이지 필드에서 여러 HTTP(S) URL을 추출해 링크마다 독립된 줄·카드로 표시했습니다.
- 공식 홈페이지는 집 아이콘, Instagram URL은 인스타그램 아이콘으로 구분합니다. Facebook·YouTube·TikTok·X 등 다른 SNS도 서비스명을 판별하고 범용 SNS 아이콘으로 표시합니다.
- URL 주소는 각 링크 카드 안에서 별도 줄로 표시해 줄바꿈과 긴 주소 줄바꿈을 보장합니다.

### 확인 기준

- 공식 홈페이지와 공식 Instagram 주소가 각각 별도 줄에 표시되고, 각 카드를 선택하면 해당 URL이 새 탭에서 열려야 합니다.
- HTML 앵커로 제공되는 홈페이지와 텍스트 URL로 제공되는 홈페이지 모두 표시되어야 합니다.

## 11. 축제 운영 시간 안내 문구 줄바꿈

### 문제

TourAPI 운영 시간 값은 공연 회차와 `※ 변경·휴무 안내`를 하나의 문자열로 제공할 수 있어, 보조 안내가 운영 시간 본문에 붙어 읽기 어려웠습니다.

### 처리

- 운영 시간 카드에서 `※`로 시작하는 안내 문구 앞에 줄바꿈을 추가했습니다.
- API가 이미 제공한 줄바꿈은 그대로 유지합니다.

### 확인 기준

- `- 매일 11:00 / 14:00 / 16:00※ 변경공휴일 공연 없음`은 운영 시간과 `※ 변경공휴일 공연 없음`이 서로 다른 줄에 표시되어야 합니다.

## 12. 축제 운영 시간의 계절·요일별 구간 줄바꿈

### 문제

운영 시간 값에 하절기·동절기 또는 요일별 시간이 `-` 구분자로 이어져 있으면, 화면 폭에 따라 임의로 줄이 꺾여 계절·요일 구간을 빠르게 구분하기 어려웠습니다.

### 처리

- 운영 시간에서 `하절기`, `동절기`, `평일`, `주말`, 요일 또는 요일 범위 앞의 `-` 구분자를 줄바꿈으로 변환했습니다.
- `※` 안내 문구 줄바꿈 처리와 함께 적용해 운영 시간의 주 정보·세부 구간·보조 안내를 구분합니다.

### 확인 기준

- `- 하절기(3월~9월) 20:00, 22:00 - 동절기(10월~2월) 19:00, 21:00`은 하절기와 동절기가 서로 다른 줄에 표시되어야 합니다.
- `- 화요일 14:00~21:00 - 수요일 09:00~13:00`은 화요일과 수요일이 서로 다른 줄에 표시되어야 합니다.

## 13. 운영 시간 형식 변형 및 한글 도메인 외부 링크 보정

### 문제

운영 시간의 구분 대시는 앞뒤 공백이나 대시 종류가 일정하지 않아 일부 요일·계절 구간이 줄바꿈되지 않았습니다. 또한 `2026전국장애학생e페스티벌.com`처럼 한글이 들어간 도메인은 ASCII 전용 URL 패턴에 잘려 공식 홈페이지·Instagram 링크가 하나의 카드에 남았습니다.

### 처리

- 공백 유무와 일반·en·em 대시를 모두 처리하고, 하절기·동절기·계절·상반기/하반기·평일/주말·요일 범위·월 또는 월 범위를 줄바꿈 대상으로 확장했습니다.
- URL 추출은 한글 도메인을 포함한 공백 전 전체 URL을 인식하도록 바꾸고, 문장 뒤에 붙는 조사·괄호·문장부호만 주소에서 제외했습니다.

### 확인 기준

- `-화요일 14:00~21:00 - 수요일 09:00~13:00`처럼 공백이 일정하지 않은 값도 요일별로 줄이 나뉘어야 합니다.
- `공식 홈페이지 http://www.2026전국장애학생e페스티벌.com/ 공식 인스타그램 https://www.instagram.com/...`은 홈페이지와 Instagram이 각각 별도 링크 카드로 표시되어야 합니다.

## 14. 여행지·행사 목록 5페이지 단위 페이지네이션

### 처리

- 여행지 탐색과 축제·행사 목록 페이지네이션에 `<<`, `>>` 형태의 5페이지 이전·다음 이동 버튼을 추가했습니다.
- 기존 한 페이지 이전·다음 버튼은 그대로 유지합니다.
- 첫 페이지에서는 이전·5페이지 이전을, 마지막 페이지에서는 다음·5페이지 다음을 비활성화하며 범위를 넘는 요청은 첫·마지막 페이지로 제한합니다.

### 확인 기준

- 8페이지에서 `<<`는 3페이지, `>>`는 마지막 범위 내 13페이지로 이동해야 합니다.
- 3페이지에서 `<<`는 1페이지, 마지막에서 `>>`는 마지막 페이지로 유지되어야 합니다.
