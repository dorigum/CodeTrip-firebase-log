# 2026-09-08 작업 로그

## 1. CodeRabbit PR #33: 삭제 진행 중 확인 모달의 키보드 포커스 이탈 방지

### 문제

게시글 삭제를 시작하면 부모 화면의 상태가 변경되며 `onCancel`·`onClose` 콜백도 새로 생성됩니다. `ConfirmModal`의 포커스 관리 effect가 이 콜백 참조까지 의존하고 있어, 모달이 열린 채로 재렌더링돼도 cleanup이 실행되고 최초 `DEL` 버튼으로 포커스를 복원할 수 있었습니다.

### 처리

- React 19의 `useEffectEvent`로 최신 콜백을 읽고, 포커스 관리 effect의 의존성은 `open`으로 한정했습니다.
- 이제 모달이 열린 상태에서 삭제 진행 여부만 바뀌어도 cleanup이 실행되지 않으며, 포커스 복원은 모달이 실제로 닫힐 때만 수행됩니다.
- Escape 동작은 최신 `onClose` 또는 `onCancel` 콜백을 읽어 기존 동작을 유지합니다.

### 확인 기준

- 삭제 중 재렌더링 뒤에도 키보드 포커스가 모달 밖의 `DEL` 버튼으로 이동하지 않아야 합니다.
- 모달을 취소·닫기하면 기존에 열었던 요소로 포커스가 복원돼야 합니다.

### 검증 결과

- `npm run lint` 통과: 오류 없음, 기존 경고 11건 유지
- `npm run build` 통과
- `git diff --check` 통과
- 별도 React DOM 테스트 도구는 프로젝트에 구성되어 있지 않아, 배포 전후 수동 키보드 점검을 함께 수행합니다.

## 2. 게시글 삭제 직후 목록에 남는 요약 카드 즉시 숨김

### 문제

게시글 원본은 클라이언트에서 즉시 삭제되지만, `boardPostSummaries/{postId}` 제거는 Database Trigger가 비동기로 처리합니다. 삭제 직후 게시판으로 이동하면 Trigger가 요약을 지우기 전 목록 요청이 먼저 실행돼, 새로고침 전까지 삭제된 카드가 보일 수 있었습니다.

### 처리

- 게시글 삭제 완료 후 게시판으로 이동할 때 삭제된 게시글 ID를 route state로 전달했습니다.
- 게시판 목록은 해당 ID를 받은 경우, Trigger 반영 전 응답에 포함되어도 즉시 제외해 렌더링합니다.
- `replace: true` 이동을 사용해 삭제된 게시글 상세 화면이 브라우저 뒤로 가기 기록에 남지 않도록 했습니다.

### 확인 기준

- 삭제 직후 게시판으로 이동해도 삭제한 게시글 카드가 보이지 않아야 합니다.
- 새로고침 후에도 Trigger가 제거한 요약이 목록에 다시 나타나지 않아야 합니다.
- 다른 게시글의 목록·페이지네이션 동작은 기존과 같아야 합니다.

## 3. 삭제 후 포커스 복원 및 목록 페이지 수 정합성 보완

### 문제

- 삭제 성공 후 라우트 전환으로 모달이 unmount될 때, 이전 상세 화면의 `DEL` 버튼으로 포커스를 복원하면 새 게시판 화면에서 유효하지 않은 요소를 가리킬 수 있었습니다.
- 목록에서 삭제된 카드를 즉시 제외했지만, offset 페이지네이션의 `totalCount`는 필터링 전 응답값을 유지할 수 있어 카드 수와 페이지 수가 일시적으로 달라질 수 있었습니다.

### 처리

- `ConfirmModal`에 선택적 `restoreFocus` 속성을 추가했습니다. 삭제 성공 경로에서는 포커스 복원 없이 모달을 먼저 닫고, state effect가 게시판 화면으로 이동합니다.
- 일반 취소·닫기 흐름은 기존처럼 모달을 열었던 요소로 포커스를 복원합니다.
- 게시판 목록이 삭제 ID를 필터링할 때, 실제 제외된 카드 수만큼 숫자형 `totalCount`도 함께 차감합니다.

### 확인 기준

- 삭제 완료 후 게시판 화면에서 키보드 포커스가 제거된 상세 화면의 `DEL` 버튼으로 복원되지 않아야 합니다.
- 검색·정렬 등 offset 페이지네이션에서도 목록 카드 수와 페이지 수가 일치해야 합니다.

## 4. Header 개인 알림 조회 범위 분리

### 문제

Header는 최신 30개의 알림만 보여주지만, 기존 개인 알림 조회는 `users/{uid}/notifications` 전체를 내려받은 뒤 클라이언트에서 정렬·제한했습니다. 알림이 누적될수록 로그인 직후 Header 조회의 다운로드량이 증가할 수 있었습니다.

### 처리

- 개인 알림의 표시용 조회를 `created_at` 정렬·최신 30개 쿼리로 제한했습니다.
- `database.rules.json`에 개인 알림 `created_at` 인덱스를 추가했습니다.
- “모두 읽음”과 “읽은 알림 삭제”는 기존 정책대로 전체 개인 알림을 조회해 오래된 알림이 누락되지 않도록 분리했습니다.
- 현재 사용자 ID를 호출 체인에서 한 번만 읽어 중복 인증 상태 조회를 제거했습니다.

### 확인 기준

- Header에는 최신 개인 알림과 TourAPI 신규 여행지 알림이 최신순으로 최대 30개 표시되어야 합니다.
- 모두 읽음·읽은 알림 삭제는 표시 수 제한과 무관하게 대상 전체에 적용되어야 합니다.
- `created_at` 인덱스가 배포된 Rules에 포함되어야 합니다.

## 5. Header 알림 상태 변경 안정성 보완

### 문제

알림의 읽음·개별 삭제·읽은 알림 일괄 삭제 요청은 네트워크 응답을 기다리는 동안 같은 버튼을 다시 누를 수 있었고, 실패 시 사용자에게 원인을 알리는 안내도 없었습니다. 특히 읽은 알림 일괄 삭제는 되돌릴 수 없는 동작인데 확인 절차가 없었습니다.

### 처리

- 알림 상태 변경 중에는 관련 버튼과 알림 행을 비활성화해 중복 요청을 막았습니다.
- 읽음 처리와 삭제 요청이 실패하면 상태를 낙관적으로 바꾸지 않고, 재시도 안내 Toast를 표시합니다.
- `읽은 알림 삭제`에는 공용 `ConfirmModal` 확인 단계를 추가했습니다. 개인 알림은 삭제되고, TourAPI 신규 여행지 알림은 사용자 목록에서만 숨김 처리된다는 범위를 문구로 안내합니다.

### 확인 기준

- 요청 중에는 알림 읽음·삭제 버튼을 연속 클릭해도 같은 요청이 중복 실행되지 않아야 합니다.
- 네트워크 또는 권한 오류 시 화면의 읽음·삭제 상태가 잘못 변경되지 않고 재시도 안내가 보여야 합니다.
- 읽은 알림 삭제는 확인 모달에서 `DELETE`를 눌렀을 때만 실행되고, 취소·닫기·Escape는 목록을 유지해야 합니다.

## 6. 관심 지역 기반 TourAPI 신규 정보 알림

### 문제

기존 TourAPI 신규 정보 알림은 공용 피드 전체를 모든 로그인 사용자에게 보여주므로, 사용자가 설정한 관심 지역과 관계없는 장소까지 Header에 노출됐습니다.

### 처리

- 공용 `tourApiUpdates/items`의 `areaCode`와 `users/{uid}/favoriteRegions`를 Header 조회 시 비교해, 일치하는 지역의 신규 항목만 표시하도록 변경했습니다.
- 관심 지역이 아직 없는 사용자는 TourAPI 신규 알림을 표시하지 않습니다. 게시글 댓글 등 기존 개인 알림에는 영향을 주지 않습니다.
- 공용 피드는 기존처럼 한 번만 저장하고 사용자별로는 읽음·숨김 상태만 저장하므로, 관심 지역별 알림을 위해 사용자 수만큼 데이터를 복제하지 않습니다.
- `contentTypeId: 15` 항목은 `[신규 축제·행사]`, 그 외 항목은 `[신규 여행지]`로 구분해 표시합니다.
- 알림 패널을 열 때 최신 관심 지역 설정을 다시 읽어, 설정 변경 뒤 새로고침하지 않아도 다음 알림 열기에서 결과가 갱신되도록 했습니다.

### 확인 기준

- 관심 지역이 서울(`11`)이면 `areaCode: 11`인 신규 장소·축제/행사만 TourAPI 알림으로 보여야 합니다.
- 관심 지역을 비우면 TourAPI 알림은 사라지고, 기존 개인 알림은 유지돼야 합니다.
- 관심 지역을 바꾼 뒤 알림 패널을 다시 열면 새 지역 기준으로 목록이 갱신돼야 합니다.
- 읽음·숨김 상태와 공용 피드 보관 정책은 기존과 같아야 합니다.

## 7. 관심 지역 코드 변환 및 알림 조회 경쟁 조건 보완

### 문제

- 사용자 관심 지역은 행정구역 코드(`11`, `26`, `41` 등)를 사용하지만 TourAPI 신규 정보의 `areaCode`는 별도 코드(`1`, `6`, `31` 등)를 사용합니다. 문자열을 그대로 비교하면 관심 지역과 일치하는 항목도 표시되지 않습니다.
- 알림 패널을 열어 시작한 조회가 읽음·삭제 요청 이후 늦게 끝나면, 이전 응답이 최신 로컬 상태를 다시 덮어쓸 수 있습니다.
- 읽은 알림 일괄 삭제 뒤에는 모달을 열었던 제어가 사라져, 기본 포커스 복원이 유효하지 않은 요소를 가리킬 수 있습니다.

### 처리

- 행정구역 코드와 TourAPI `areaCode` 간 변환 유틸리티를 추가하고, 배열·객체 형식의 관심 지역 데이터를 모두 처리하도록 했습니다. 숫자 `31`, `36`처럼 두 체계에서 의미가 충돌하는 값이 있어, 사용자 설정 값은 행정구역 코드로 일관되게 해석합니다.
- 알림 조회에 요청 세대를 부여해 가장 최근 요청만 목록·미읽음 수 상태를 변경하게 했습니다. 읽음·삭제 성공 시 이전 조회 세대를 무효화합니다.
- 읽은 알림 일괄 삭제 성공 시 모달의 자동 포커스 복원을 끄고 Header 알림 벨로 포커스를 옮깁니다. 취소·닫기 시에는 기존 포커스 복원 동작을 유지합니다.

### 확인 기준

- 서울 관심 지역 `11`은 TourAPI `areaCode: 1`, 부산 `26`은 `areaCode: 6` 항목과 일치해야 합니다.
- 알림 조회 중 읽음·삭제를 수행해도 이전 조회 결과가 최신 상태를 덮어쓰지 않아야 합니다.
- 읽은 알림 일괄 삭제 뒤 키보드 포커스는 Header 알림 벨에 있어야 하고, 취소·닫기는 기존 제어로 복원돼야 합니다.

## 10. TourAPI 주소 기반 지역 코드 보완 및 기존 알림 백필

### 문제

- `KorService2.areaBasedList2` 최신 항목 응답의 `areacode`가 비어 있는 사례가 확인됐습니다.
- Header는 사용자 관심 지역 행정구역 코드를 TourAPI 지역 코드로 변환해 `tourApiUpdates/items/{contentId}/areaCode`와 비교하므로, 공용 항목의 코드가 비어 있으면 모든 관심 지역 알림이 제외됩니다.

### 처리

- TourAPI 원본 `areacode`를 우선 사용하고, 값이 없으면 `addr1`의 시·도 접두어로 TourAPI 지역 코드를 보완합니다. 예를 들어 `대전광역시`는 `3`, `경기도`는 `31`로 기록됩니다.
- 이미 존재하는 `contentId`는 신규 항목으로 다시 저장하지 않습니다. 다만 저장된 `areaCode`가 비어 있거나 달라진 경우에만 해당 필드만 갱신해, 초기 동기화로 생성된 30개 항목도 다음 성공 실행에서 보정됩니다.
- 주소 기반 코드 보완의 대표 사례를 Functions 단위 테스트에 추가했습니다.

### 확인 기준

- 다음 `syncTourApiUpdates` 성공 실행 뒤 기존 `tourApiUpdates/items` 항목에 `areaCode`가 채워져야 합니다.
- 대전 관심 지역(행정구역 코드 `30`) 사용자는 `areaCode: 3` 항목을, 경기 관심 지역(`41`) 사용자는 `areaCode: 31` 항목을 Header에서 확인할 수 있어야 합니다.
- 이미 올바른 코드가 저장된 항목은 매 실행마다 다시 쓰지 않아야 합니다.

## 11. TourAPI 연결 실패 재시도 및 원인 로그 보강

### 문제

- Cloud Scheduler 수동 실행에서 `syncTourApiUpdates`가 HTTP `500`으로 실패했고, Cloud Run 로그에는 HTTP 상태 코드 없이 `Error: fetch failed`만 남았습니다.
- 이는 TourAPI 서버가 응답을 보내기 전에 연결이 끊긴 경우로, 기존 함수는 한 번의 일시적 네트워크 실패도 즉시 스케줄 실패로 처리했습니다.

### 처리

- TourAPI 조회에 15초 요청 제한과 최대 2회 재시도를 적용했습니다. 연결 실패, 시간 초과, HTTP 408 및 5xx 응답만 재시도하며, 인증·권한 오류 같은 4xx 응답은 불필요하게 반복하지 않습니다.
- 재시도 시도 횟수와 HTTP 상태, 연결 오류의 이름·메시지·하위 원인 코드를 구조화 로그로 남겨 다음 장애에서 `fetch failed` 원인을 확인할 수 있게 했습니다.

### 확인 기준

- 일시적인 연결 실패는 최대 세 번의 시도 안에서 성공하면 Scheduler 실행이 성공으로 끝나야 합니다.
- 모두 실패하면 Cloud Logging에서 `causeCode` 또는 `causeMessage`로 DNS·연결·시간 초과 원인을 확인할 수 있어야 합니다.
- `403` 같은 비재시도 가능 오류는 즉시 실패 처리되어 불필요한 외부 API 호출을 만들지 않아야 합니다.

## 12. 축제 전용 수집 및 TourAPI 알림 수신 설정 1차 구현

- `searchFestival2`를 동일한 스케줄 동기화에 추가하고, 일반 최신 목록과 겹치는 `contentId`는 축제 소스를 우선해 한 번만 보관합니다.
- 설정 화면에서 관심 지역 신규 여행지·축제 알림 수신 여부를 저장할 수 있게 했습니다. 기본값은 수신이며, 해제해도 개인 알림은 유지됩니다.
