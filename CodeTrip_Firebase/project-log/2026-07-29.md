# 2026-07-29 작업 로그

## 1. 작업 개요

`feature/cache` 브랜치에서 메인 화면 진입 시 반복 호출될 수 있는 날씨 API와 위치명 역지오코딩 API 호출 구조를 분석하고, 기존 공공데이터 API 캐시 레이어를 날씨/지역 API에도 재사용하도록 보완했습니다.

기존 TourAPI 여행지 목록, 키워드 검색, 상세 정보, 사진 API는 `src/api/apiCache.js`의 메모리, localStorage, Firebase Realtime Database 공유 캐시를 이미 사용하고 있었습니다. 반면 `src/api/weatherApi.js`의 `getWeather()`와 `getLocationName()`은 외부 API를 직접 호출하고 있어 홈 화면 진입, 현재 위치 갱신, 슬롯 추천 흐름에서 반복 호출될 가능성이 있었습니다.

## 2. 기존 캐시 구조 분석

- `src/api/apiCache.js`
  - 메모리 캐시, localStorage, Firebase Realtime Database `apiCache/{cacheKey}`를 순차 조회하는 공통 캐시 레이어입니다.
  - 캐시가 만료되었거나 없으면 실제 API를 호출하고, 성공 시 메모리, localStorage, Realtime Database에 같은 응답을 저장합니다.
  - API 호출 실패 시 만료된 캐시라도 존재하면 fallback 데이터로 반환합니다.

- `src/api/travelInfoApi.js`
  - TourAPI 목록, 검색, 상세, 이미지, 지역 코드 조회에 `cachedApiRequest()`를 사용하고 있었습니다.
  - 목록 12시간, 키워드 검색 6시간, 상세 정보 14일, 지역 코드 30일 TTL이 적용되어 있었습니다.

- `src/api/travelApi.js`
  - 관광 사진 API도 `cachedApiRequest()`를 사용하고 있었습니다.
  - 축제/행사 API는 내부적으로 `getTravelInfo()`를 호출하므로 TourAPI 캐시를 함께 사용합니다.

- `src/api/weatherApi.js`
  - Open-Meteo 현재 날씨 API와 Nominatim reverse geocoding API는 캐시 없이 매번 직접 호출하고 있었습니다.

## 3. 날씨 API 캐시 적용

`src/api/weatherApi.js`의 `getWeather()`에 기존 `cachedApiRequest()`를 연결했습니다.

적용 정책은 아래와 같습니다.

- 캐시 scope: `weather`
- 서비스명: `openMeteoCurrent`
- TTL: 1시간
- 캐시 키 기준: 위도/경도를 소수점 2자리로 반올림한 값

날씨는 시간에 따라 바뀌는 데이터이므로 너무 길게 캐시하지 않고 1시간 TTL로 설정했습니다. 좌표는 소수점 2자리로 묶어 같은 생활권 주변에서는 동일 캐시를 공유하도록 했습니다.

## 4. 위치명 역지오코딩 캐시 적용

`src/api/weatherApi.js`의 `getLocationName()`에도 `cachedApiRequest()`를 적용했습니다.

적용 정책은 아래와 같습니다.

- 캐시 scope: `location`
- 서비스명: `nominatimReverse`
- TTL: 30일
- 캐시 키 기준: 위도/경도를 소수점 3자리로 반올림한 값

지역명은 날씨보다 변동성이 낮으므로 30일 TTL을 적용했습니다. 좌표는 소수점 3자리로 반올림해 너무 넓은 지역이 같은 캐시로 묶이지 않도록 조정했습니다.

## 8. 트러블슈팅

### 8.1 날씨/지역 API가 캐시 없이 반복 호출될 수 있는 구조

- **현상**: TourAPI 계열은 캐시가 적용되어 있었지만, 날씨와 위치명 조회는 API 함수 내부에서 직접 외부 API를 호출하고 있었습니다.
- **원인**: Firebase 전환 당시 공공데이터 API 호출량 절감을 위해 `apiCache` 레이어를 추가했지만, 날씨/위치 API는 별도 파일에서 관리되어 공통 캐시 적용 대상에서 빠져 있었습니다.
- **처리**:
  - `getWeather()`에 `cachedApiRequest()` 적용
  - `getLocationName()`에 `cachedApiRequest()` 적용
  - 좌표 반올림 기반 캐시 키를 추가해 근처 위치의 중복 호출을 줄이도록 구성
- **확인**: ESLint와 production build를 통해 import 및 번들링 문제가 없는 것을 확인했습니다.

### 8.2 Vite build 임시 파일 생성 권한 오류

- **현상**: `npm run build` 실행 시 Vite가 `node_modules/.vite-temp` 하위 임시 파일을 생성하지 못해 `EPERM` 오류가 발생했습니다.
- **원인**: 현재 Codex 실행 환경이 읽기 제한을 가진 sandbox 상태였고, Vite build는 설정 파일 로딩 과정에서 임시 파일을 생성해야 합니다.
- **처리**: 동일 명령을 권한 상승 후 재실행했습니다.
- **확인**: 권한 상승 후 `npm run build`가 정상 완료되었습니다.

AI 여행 코스 상세 문서에서 여러 날짜의 일정이 한 화면에 모두 펼쳐지는 문제를 줄이기 위해 날짜별 탭 UI를 추가했습니다.

### 12.1 변경 내용

  - 탭을 선택하면 해당 날짜의 일정만 상세 영역에 렌더링되도록 변경했습니다.
  - AI 코스 문서를 열 때 항상 첫 번째 날짜 탭부터 보이도록 초기화했습니다.
  - 코스 재생성 등으로 날짜 수가 바뀌어도 렌더링 단계에서 활성 날짜 인덱스를 안전하게 보정하도록 처리했습니다.

### 12.2 적용 이유

- 모바일 화면에서는 전체 일정이 한 번에 펼쳐질수록 스크롤 부담이 커지므로 날짜별 탐색이 더 적합합니다.
- 추후 장소 카드 접기/펼치기 기능을 추가하기 전, 날짜 단위 탐색 구조를 먼저 잡는 것이 안전합니다.

### 12.3 확인 필요

- 1일 코스 상세 문서에서 탭 없이 일정이 표시되는지 확인
- 2일 이상 코스 상세 문서에서 날짜 탭이 표시되는지 확인
- `DAY 1`, `DAY 2` 탭을 전환할 때 해당 날짜 일정만 표시되는지 확인
- 코스 문서를 닫았다 다시 열면 첫 번째 날짜 탭으로 초기화되는지 확인

  - 장소 카드를 클릭하면 주소, 추천 이유, 팁을 상세 영역으로 펼쳐 보여주도록 처리했습니다.
  - 펼침 상태는 AI 코스 문서를 새로 열거나 날짜 탭을 전환할 때 초기화되도록 구성했습니다.
  - 추가 상세 정보가 없는 장소에는 `// no_extra_place_detail` 빈 상태 문구를 표시하도록 처리했습니다.
  - AI 코스 상세 모달의 데스크톱 레이아웃에서 본문 전체가 하나의 스크롤 영역으로 동작하도록 overflow 구조를 보정했습니다.

### 13.2 적용 이유

- AI 코스 문서가 길어질수록 사용자가 전체 일정의 시간 흐름을 먼저 확인하기 어려웠습니다.
- 장소별 상세 설명은 필요할 때만 열어보는 방식이 모바일 화면에서 더 적합합니다.
- 날짜별 탭과 함께 사용하면 `DAY` 단위 탐색 후 장소 단위 상세 확인까지 자연스럽게 이어집니다.
- 기존에는 데스크톱 크기에서 모달 본문이 일부 영역별로만 스크롤되어, 레거시 코스 문서처럼 내용이 긴 경우 하단 버튼과 상세 정보까지 접근하기 어려울 수 있었습니다.

### 13.3 확인 필요

- AI 코스 상세 문서에서 장소 카드가 기본 축약 상태로 표시되는지 확인
- 장소 카드를 클릭했을 때 주소, 추천 이유, 팁이 펼쳐지는지 확인
- 다시 클릭하면 축약 상태로 돌아가는지 확인
- 날짜 탭을 전환하면 이전 날짜에서 펼쳤던 장소 카드 상태가 초기화되는지 확인
- 모바일 크기에서 장소 카드가 과하게 길게 늘어지지 않고 읽기 편한지 확인
- 레거시 AI 코스 문서처럼 본문이 긴 상세 모달에서도 하단까지 스크롤되는지 확인

## 14. AI 코스 문서와 저장 여행지 카드 연결 강화

AI 코스 상세 문서에서 공식 여행지와 문서 전용 추천 장소의 후속 행동이 명확하지 않아, 장소 출처에 따라 상세 보기 연결 여부를 분리했습니다.

### 14.1 변경 내용

- `src/pages/MyPage.jsx`
  - AI 코스 장소 데이터에서 `contentId`, `contentid`, `content_id`를 공통으로 읽는 `getPlanContentId()` 헬퍼를 추가했습니다.
  - 관광공사 contentId가 있는 공식 여행지/공식 후보 장소에는 `View_Data` 버튼을 표시하도록 변경했습니다.
  - `View_Data` 버튼을 누르면 기존 여행지 상세 경로(`/explore/:contentId`)로 이동하도록 연결했습니다.
  - 공식 장소에는 `저장 여행지 카드와 연결됨` 안내 배지를 표시했습니다.
  - contentId가 없는 코스 추천 장소에는 `문서 전용 추천 장소` 안내 문구를 표시했습니다.

### 14.2 적용 이유

- AI 코스에는 관광공사 검증 장소와 CodeTrip이 일정 완성을 위해 제안한 장소가 함께 섞일 수 있습니다.
- 공식 여행지는 상세 정보, 지도, 이미지, 댓글 등 기존 여행지 상세 페이지와 연결되는 것이 자연스럽습니다.
- 반대로 코스 추천 장소는 위시리스트 카드로 저장되지 않는 문서 보관용 데이터이므로, 사용자가 삭제되었거나 저장 실패한 데이터로 오해하지 않도록 안내가 필요했습니다.

### 14.3 확인 필요

- 공식 여행지 또는 공식 후보 장소를 펼쳤을 때 `View_Data` 버튼이 표시되는지 확인
- `View_Data` 버튼 클릭 시 해당 여행지 상세 페이지로 이동하는지 확인
- 코스 추천 장소를 펼쳤을 때 문서 전용 추천 장소 안내가 표시되는지 확인
- contentId가 없는 장소에는 상세 보기 버튼이 표시되지 않는지 확인

## 15. AI 코스 상세 상단 요약 및 메모 작성 기능 추가

AI 코스 상세 문서에서 상단 요약과 하단 `LEGACY_COURSE_CONTENT`가 동일하게 길게 노출되어 중복처럼 보이는 문제를 줄이고, 코스 문서 안에서도 메모를 바로 작성할 수 있도록 개선했습니다.

### 15.1 변경 내용

- `src/pages/MyPage.jsx`
  - AI 코스 상세 상단의 blockquote 영역에 `getCourseSummaryPreview()`를 적용했습니다.
  - 저장된 `summary` 또는 `legacy_content`에서 제목과 시간표 시작 구간을 제외하고, 앞부분 2문장 내외만 요약으로 표시하도록 처리했습니다.
  - 긴 요약은 180자 기준으로 축약해 상단 설명이 하단 원문과 동일하게 길어지지 않도록 정리했습니다.
  - AI 코스 상세 오른쪽 패널의 `Course_Checklist` 아래에 `Course_Memo` 섹션을 추가했습니다.
  - 같은 폴더의 `MEMO` 타입 노트를 표시하고, 상세 모달 안에서 새 메모를 바로 작성할 수 있도록 연결했습니다.
  - 레거시 AI 코스 메모(`[AI 여행 코스]`로 시작하는 기존 메모)는 `Course_Memo` 목록에서 제외했습니다.
  - AI 코스 문서를 열거나 닫을 때 작성 중인 메모 입력값이 초기화되도록 처리했습니다.

### 15.2 적용 이유

- 레거시 코스 문서는 구조화된 `days` 데이터가 없어서 상단 요약과 하단 원문이 같은 내용처럼 보일 수 있었습니다.
- 상단은 코스 전체를 빠르게 이해하는 요약 영역으로 두고, 하단은 원문 또는 날짜별 상세 코스를 확인하는 영역으로 역할을 분리하는 편이 자연스럽습니다.
- 여행 준비 과정에서 체크리스트뿐 아니라 간단한 메모도 같은 코스 상세 화면에서 남길 수 있어야 실제 사용 흐름이 이어집니다.

### 15.3 확인 필요

- 레거시 AI 코스 상세 문서에서 상단 요약이 하단 원문보다 짧게 표시되는지 확인
- 일반 AI 코스 상세 문서에서도 상단 요약이 과하게 길게 늘어나지 않는지 확인
- `Course_Memo`에서 기존 폴더 메모가 표시되는지 확인
- `Course_Memo` 입력 후 새 메모가 같은 폴더 메모로 저장되는지 확인
- AI 코스 문서를 닫았다 다시 열었을 때 작성 중이던 입력값이 남지 않는지 확인
