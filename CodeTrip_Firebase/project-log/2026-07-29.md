# 2026-07-29 작업 로그

## 1. 작업 개요

`feature/cache` 브랜치에서 메인 화면 진입 시 반복 호출될 수 있는 날씨 API와 위치명 역지오코딩 API 호출 구조를 분석하고, 기존 공공데이터 API 캐시 레이어를 날씨/지역 API에도 재사용하도록 보완했습니다.

기존 TourAPI 여행지 목록, 키워드 검색, 상세 정보, 사진 API는 `src/api/apiCache.js`의 메모리, localStorage, Firebase Realtime Database 공유 캐시를 이미 사용하고 있었습니다. 반면 `src/api/weatherApi.js`의 `getWeather()`와 `getLocationName()`은 외부 API를 직접 호출하고 있어 홈 화면 진입, 현재 위치 갱신, 슬롯 추천 흐름에서 반복 호출될 가능성이 있었습니다.

## 2. 기존 캐시 구조 분석

- `src/api/apiCache.js`
  - 메모리 캐시, localStorage, Firebase Realtime Database `apiCache/{cacheKey}`를 순차 조회하는 공통 캐시 레이어입니다.
  - 캐시가 만료되었거나 없으면 실제 API를 호출하고, 성공 시 메모리, localStorage, Realtime Database에 같은 응답을 저장합니다.
  - API 호출 실패 시 만료된 캐시라도 존재하면 fallback 데이터로 반환합니다.

- `src/api/travelInfoApi.js`
  - TourAPI 목록, 검색, 상세, 이미지, 지역 코드 조회에 `cachedApiRequest()`를 사용하고 있었습니다.
  - 목록 12시간, 키워드 검색 6시간, 상세 정보 14일, 지역 코드 30일 TTL이 적용되어 있었습니다.

- `src/api/travelApi.js`
  - 관광 사진 API도 `cachedApiRequest()`를 사용하고 있었습니다.
  - 축제/행사 API는 내부적으로 `getTravelInfo()`를 호출하므로 TourAPI 캐시를 함께 사용합니다.

- `src/api/weatherApi.js`
  - Open-Meteo 현재 날씨 API와 Nominatim reverse geocoding API는 캐시 없이 매번 직접 호출하고 있었습니다.

## 3. 날씨 API 캐시 적용

`src/api/weatherApi.js`의 `getWeather()`에 기존 `cachedApiRequest()`를 연결했습니다.

적용 정책은 아래와 같습니다.

- 캐시 scope: `weather`
- 서비스명: `openMeteoCurrent`
- TTL: 1시간
- 캐시 키 기준: 위도/경도를 소수점 2자리로 반올림한 값

날씨는 시간에 따라 바뀌는 데이터이므로 너무 길게 캐시하지 않고 1시간 TTL로 설정했습니다. 좌표는 소수점 2자리로 묶어 같은 생활권 주변에서는 동일 캐시를 공유하도록 했습니다.

## 4. 위치명 역지오코딩 캐시 적용

`src/api/weatherApi.js`의 `getLocationName()`에도 `cachedApiRequest()`를 적용했습니다.

적용 정책은 아래와 같습니다.

- 캐시 scope: `location`
- 서비스명: `nominatimReverse`
- TTL: 30일
- 캐시 키 기준: 위도/경도를 소수점 3자리로 반올림한 값

지역명은 날씨보다 변동성이 낮으므로 30일 TTL을 적용했습니다. 좌표는 소수점 3자리로 반올림해 너무 넓은 지역이 같은 캐시로 묶이지 않도록 조정했습니다.

## 8. 트러블슈팅

### 8.1 날씨/지역 API가 캐시 없이 반복 호출될 수 있는 구조

- **현상**: TourAPI 계열은 캐시가 적용되어 있었지만, 날씨와 위치명 조회는 API 함수 내부에서 직접 외부 API를 호출하고 있었습니다.
- **원인**: Firebase 전환 당시 공공데이터 API 호출량 절감을 위해 `apiCache` 레이어를 추가했지만, 날씨/위치 API는 별도 파일에서 관리되어 공통 캐시 적용 대상에서 빠져 있었습니다.
- **처리**:
  - `getWeather()`에 `cachedApiRequest()` 적용
  - `getLocationName()`에 `cachedApiRequest()` 적용
  - 좌표 반올림 기반 캐시 키를 추가해 근처 위치의 중복 호출을 줄이도록 구성
- **확인**: ESLint와 production build를 통해 import 및 번들링 문제가 없는 것을 확인했습니다.

### 8.2 Vite build 임시 파일 생성 권한 오류

- **현상**: `npm run build` 실행 시 Vite가 `node_modules/.vite-temp` 하위 임시 파일을 생성하지 못해 `EPERM` 오류가 발생했습니다.
- **원인**: 현재 Codex 실행 환경이 읽기 제한을 가진 sandbox 상태였고, Vite build는 설정 파일 로딩 과정에서 임시 파일을 생성해야 합니다.
- **처리**: 동일 명령을 권한 상승 후 재실행했습니다.
- **확인**: 권한 상승 후 `npm run build`가 정상 완료되었습니다.

AI 여행 코스 상세 문서에서 여러 날짜의 일정이 한 화면에 모두 펼쳐지는 문제를 줄이기 위해 날짜별 탭 UI를 추가했습니다.

### 12.1 변경 내용

  - 탭을 선택하면 해당 날짜의 일정만 상세 영역에 렌더링되도록 변경했습니다.
  - AI 코스 문서를 열 때 항상 첫 번째 날짜 탭부터 보이도록 초기화했습니다.
  - 코스 재생성 등으로 날짜 수가 바뀌어도 렌더링 단계에서 활성 날짜 인덱스를 안전하게 보정하도록 처리했습니다.

### 12.2 적용 이유

- 모바일 화면에서는 전체 일정이 한 번에 펼쳐질수록 스크롤 부담이 커지므로 날짜별 탐색이 더 적합합니다.
- 추후 장소 카드 접기/펼치기 기능을 추가하기 전, 날짜 단위 탐색 구조를 먼저 잡는 것이 안전합니다.

### 12.3 확인 필요

- 1일 코스 상세 문서에서 탭 없이 일정이 표시되는지 확인
- 2일 이상 코스 상세 문서에서 날짜 탭이 표시되는지 확인
- `DAY 1`, `DAY 2` 탭을 전환할 때 해당 날짜 일정만 표시되는지 확인
- 코스 문서를 닫았다 다시 열면 첫 번째 날짜 탭으로 초기화되는지 확인

  - 펼침 상태는 AI 코스 문서를 새로 열거나 날짜 탭을 전환할 때 초기화되도록 구성했습니다.
  - 추가 상세 정보가 없는 장소에는 `// no_extra_place_detail` 빈 상태 문구를 표시하도록 처리했습니다.
  - AI 코스 상세 모달의 데스크톱 레이아웃에서 본문 전체가 하나의 스크롤 영역으로 동작하도록 overflow 구조를 보정했습니다.

### 13.2 적용 이유

- AI 코스 문서가 길어질수록 사용자가 전체 일정의 시간 흐름을 먼저 확인하기 어려웠습니다.
- 장소별 상세 설명은 필요할 때만 열어보는 방식이 모바일 화면에서 더 적합합니다.

### 13.3 확인 필요

- 장소 카드를 클릭했을 때 주소, 추천 이유, 팁이 펼쳐지는지 확인
- 다시 클릭하면 축약 상태로 돌아가는지 확인
- 날짜 탭을 전환하면 이전 날짜에서 펼쳤던 장소 카드 상태가 초기화되는지 확인
- 모바일 크기에서 장소 카드가 과하게 길게 늘어지지 않고 읽기 편한지 확인
- 레거시 AI 코스 문서처럼 본문이 긴 상세 모달에서도 하단까지 스크롤되는지 확인

## 15. AI 코스 상세 상단 요약 및 메모 작성 기능 추가

AI 코스 상세 문서에서 상단 요약과 하단 `LEGACY_COURSE_CONTENT`가 동일하게 길게 노출되어 중복처럼 보이는 문제를 줄이고, 코스 문서 안에서도 메모를 바로 작성할 수 있도록 개선했습니다.

### 15.1 변경 내용

- `src/pages/MyPage.jsx`
  - AI 코스 상세 상단의 blockquote 영역에 `getCourseSummaryPreview()`를 적용했습니다.
  - 저장된 `summary` 또는 `legacy_content`에서 제목과 시간표 시작 구간을 제외하고, 앞부분 2문장 내외만 요약으로 표시하도록 처리했습니다.
  - 긴 요약은 180자 기준으로 축약해 상단 설명이 하단 원문과 동일하게 길어지지 않도록 정리했습니다.
  - AI 코스 상세 오른쪽 패널의 `Course_Checklist` 아래에 `Course_Memo` 섹션을 추가했습니다.

  - 레거시 AI 코스 메모(`[AI 여행 코스]`로 시작하는 기존 메모)는 `Course_Memo` 목록에서 제외했습니다.
  - AI 코스 문서를 열거나 닫을 때 작성 중인 메모 입력값이 초기화되도록 처리했습니다.

### 15.2 적용 이유

- 레거시 코스 문서는 구조화된 `days` 데이터가 없어서 상단 요약과 하단 원문이 같은 내용처럼 보일 수 있었습니다.
- 상단은 코스 전체를 빠르게 이해하는 요약 영역으로 두고, 하단은 원문 또는 날짜별 상세 코스를 확인하는 영역으로 역할을 분리하는 편이 자연스럽습니다.
- 여행 준비 과정에서 체크리스트뿐 아니라 간단한 메모도 같은 코스 상세 화면에서 남길 수 있어야 실제 사용 흐름이 이어집니다.

### 15.3 확인 필요

- 레거시 AI 코스 상세 문서에서 상단 요약이 하단 원문보다 짧게 표시되는지 확인
- 일반 AI 코스 상세 문서에서도 상단 요약이 과하게 길게 늘어나지 않는지 확인
- `Course_Memo`에서 기존 폴더 메모가 표시되는지 확인
- `Course_Memo` 입력 후 새 메모가 같은 폴더 메모로 저장되는지 확인
- AI 코스 문서를 닫았다 다시 열었을 때 작성 중이던 입력값이 남지 않는지 확인

## 16. 축제 정보 조회 로직 개편

축제 정보 페이지가 일반 여행지 목록 API에 `contentTypeId=15`만 적용하는 구조라 현재 진행 중이거나 예정된 축제를 안정적으로 보여주기 어려웠습니다. 축제 전용 API를 사용하도록 공통 API 계층을 정리했습니다.

### 16.3 확인 필요

- `/festivals`에서 현재 진행 중이거나 예정된 축제가 표시되는지 확인
- `DEFAULT_NODES`, `DATE_ASCENDING`, `DATE_DESCENDING` 정렬이 날짜 기준으로 동작하는지 확인
- 페이지네이션이 필터링된 축제 개수 기준으로 정상 표시되는지 확인

### 19.3 확인 필요

- 축제 기간이 `YYYY.MM.DD ~ YYYY.MM.DD` 형식으로 표시되는지 확인
- 홈페이지가 있는 축제에서 외부 링크가 새 탭으로 열리는지 확인
- 일반 여행지 상세 페이지에는 축제 전용 카드가 표시되지 않는지 확인

## 20. 개발용 API 캐시 상태 확인 UI 추가

날씨/위치/관광공사 API 호출 최소화 작업 이후, 로컬 테스트 중 특정 응답이 캐시에서 온 것인지 네트워크에서 새로 받아온 것인지 확인하기 어려웠습니다. 개발 환경에서만 표시되는 작은 캐시 상태 패널을 추가해 캐시 동작을 빠르게 점검할 수 있도록 했습니다.

### 20.1 변경 내용

- `src/api/apiCache.js`
  - `cachedApiRequest()`가 메모리, localStorage, Realtime Database, 네트워크, stale cache 중 어떤 경로로 응답했는지 브라우저 이벤트로 발행하도록 보완했습니다.
  - 이벤트 이름은 `codetrip:api-cache-status`로 정리했습니다.
  - 개발 환경(`import.meta.env.DEV`)에서만 이벤트를 발행하도록 제한했습니다.

- `src/components/ApiCacheStatus.jsx`
  - 최근 API 캐시 상태를 표시하는 개발용 고정 패널을 추가했습니다.
  - `MEMORY`, `LOCAL`, `REMOTE_DB`, `NETWORK`, `STALE_CACHE` 상태를 구분해 보여주도록 구성했습니다.
  - 모바일 화면에서는 노출하지 않고 데스크톱 개발 검증용으로만 표시되도록 처리했습니다.

- `src/App.jsx`
  - 앱 루트에 `ApiCacheStatus` 컴포넌트를 연결했습니다.

### 20.2 적용 이유

- 날씨/위치 API는 사용자 위치와 홈 화면 진입 흐름에서 반복 호출될 수 있어 캐시 적용 여부를 직접 확인할 수 있어야 합니다.
- 콘솔 로그만으로 확인하면 놓치기 쉬워, 로컬 화면에 작고 명확한 상태 패널을 두는 편이 테스트 효율이 좋습니다.
- 배포 환경에서는 사용자에게 불필요한 디버그 정보가 보이면 안 되므로 개발 환경 전용으로 제한했습니다.

### 20.3 확인 필요

- 로컬 개발 서버에서 홈 화면 진입 시 `api_cache.log` 패널이 표시되는지 확인
- 첫 호출 이후 같은 조건으로 재진입했을 때 `NETWORK`가 아닌 `MEMORY` 또는 `LOCAL` 상태로 표시되는지 확인
- 프로덕션 빌드 화면에서는 캐시 상태 패널이 표시되지 않는지 확인

## 21. 상단 검색창 통합 동작 정리

상단 공통 헤더의 검색창이 최근 검색어만 저장하고 실제 페이지별 검색 조건과 명확하게 연결되지 않는 문제가 있어, URL 파라미터 기반 검색 흐름으로 정리했습니다. 이제 탐색 페이지에서는 여행지 검색으로, 축제 정보 페이지에서는 축제 검색으로 동작합니다.

### 21.1 변경 내용

- `src/components/Layout/Header.jsx`
  - 검색어 입력 후 Enter를 누르면 현재 위치에 따라 `/explore?keyword=...` 또는 `/festivals?keyword=...`로 이동하도록 변경했습니다.
  - 축제 정보 페이지에서 검색할 경우 기존 `region`, `sort` 조건을 유지하고 `page=1`로 초기화하도록 처리했습니다.
  - 빈 검색어 입력 시 브라우저 기본 alert 대신 프로젝트 토스트 메시지를 사용하도록 변경했습니다.
  - 최근 검색어 클릭 시에도 동일한 URL 기반 검색 흐름을 사용하도록 정리했습니다.

- `src/pages/Explore.jsx`
  - URL의 `keyword` 값을 탐색 스토어 검색어와 동기화하도록 연결했습니다.
  - 검색 배지의 닫기 버튼을 누르면 검색어를 초기화하고 `/explore` 기본 목록으로 돌아가도록 변경했습니다.

- `src/pages/Festivals.jsx`
  - URL의 `keyword` 값을 축제 조회 조건에 포함했습니다.
  - 축제 검색 상태를 `// searching_festivals:` 배지로 표시하고, 닫기 버튼으로 검색 조건을 해제할 수 있도록 추가했습니다.

- `src/api/travelApi.js`, `src/api/travelInfoApi.js`
  - `getFestivalList()`와 `getFestivalInfo()`에 `keyword` 조건을 추가했습니다.
  - 진행 중이거나 예정된 축제 목록 중 제목, 주소, 설명에 검색어가 포함된 항목만 필터링하도록 보완했습니다.

### 21.2 적용 이유

- 공통 헤더 검색창이 페이지 상태와 분리되어 있으면 사용자는 검색이 적용되었는지 확인하기 어렵습니다.
- URL 파라미터로 검색 상태를 관리하면 새로고침, 뒤로가기, 링크 공유 시에도 동일한 검색 결과를 유지할 수 있습니다.
- 축제 정보 페이지는 여행지 탐색과 다른 데이터 흐름을 사용하므로, 현재 페이지에 맞춰 검색 대상을 분리하는 방식이 더 자연스럽습니다.

### 21.3 확인 필요

- 홈 또는 일반 페이지에서 검색 시 `/explore?keyword=검색어&page=1`로 이동하는지 확인
- 축제 정보 페이지에서 검색 시 `/festivals?keyword=검색어&page=1`로 이동하고 기존 지역/정렬 조건이 유지되는지 확인
- 탐색/축제 페이지에서 검색 배지 닫기 버튼을 누르면 기본 목록으로 돌아가는지 확인
- 최근 검색어 클릭 시에도 동일한 검색 결과가 표시되는지 확인

## 22. 축제 정보 시군구 필터 확장

축제 정보 페이지의 지역 필터가 시도 단위까지만 제공되어, 경기처럼 축제 데이터가 많은 지역에서는 원하는 축제를 좁혀 찾기 어려운 문제가 있었습니다. 선택한 시도에 따라 하위 시군구 목록을 불러오고, 축제 조회 조건에 시군구 코드를 함께 전달하도록 확장했습니다.

### 22.1 변경 내용

- `src/api/travelInfoApi.js`
  - `ldongCode2`를 사용해 선택한 시도의 하위 시군구 목록을 조회하는 `getSubRegions()` 함수를 추가했습니다.
  - 축제 조회 함수 `getFestivalInfo()`가 `lDongSignguCd`를 받을 수 있도록 확장했습니다.
  - `searchFestival2` 요청 시 `lDongRegnCd`와 `lDongSignguCd`를 함께 전달할 수 있도록 공통 요청 파라미터를 정리했습니다.

- `src/api/travelApi.js`
  - `getFestivalList()`에 `subRegion` 인자를 추가하고, 하위 API로 시군구 코드를 전달하도록 변경했습니다.

- `src/pages/Festivals.jsx`
  - URL 파라미터 `sigungu`를 추가로 읽고 유지하도록 변경했습니다.
  - 시도 선택 시 해당 시도의 시군구 목록을 비동기로 불러오는 로직을 추가했습니다.
  - 시도 선택값이 없거나 시군구 목록이 없을 때는 시군구 드롭다운을 비활성화하도록 처리했습니다.
  - 시도를 변경하면 기존 시군구 선택이 초기화되도록 처리했습니다.
  - 잘못된 시군구 코드가 URL에 남아 있을 경우 자동으로 초기화되도록 방어 로직을 추가했습니다.

### 22.2 적용 이유

- 축제 정보는 지역 기반 탐색 비중이 높아, 시도 단위 필터만으로는 사용자가 원하는 범위를 빠르게 좁히기 어렵습니다.
- 기존 지역 필터 구조를 유지하면서 시군구만 보조 필터로 추가하면 UI 변화가 크지 않고, 사용자가 기존 흐름을 그대로 사용할 수 있습니다.
- URL 파라미터에 시군구 선택값을 남기면 새로고침이나 링크 공유 시에도 같은 필터 결과를 유지할 수 있습니다.

### 22.3 확인 필요

- 축제 정보 페이지에서 시도 선택 시 시군구 드롭다운이 활성화되는지 확인
- 시군구 선택 후 해당 지역 축제만 표시되는지 확인
- 시도를 변경하면 기존 시군구 선택이 초기화되는지 확인
- 검색어, 시도, 시군구, 정렬 조건이 함께 적용되는지 확인
- 시군구 필터가 없는 전국 상태에서는 기존 축제 목록 조회가 정상 동작하는지 확인
