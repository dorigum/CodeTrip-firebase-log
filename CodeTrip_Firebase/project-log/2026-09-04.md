# 2026-09-04 작업 로그

## 1. 새로고침 시 비회원 홈 화면이 일시적으로 노출되는 인증 복원 깜빡임 보정

### 문제

로그인한 사용자가 홈에서 새로고침하면 Firebase Authentication의 `onAuthStateChanged()`가 세션을 복원하기 전에 홈이 `isLoggedIn: false`를 기준으로 비회원 화면을 먼저 렌더링했습니다. 인증 콜백이 완료된 뒤 회원 홈으로 다시 전환되어 화면이 순간적으로 바뀌었습니다.

### 원인

인증 스토어는 초기 상태를 `isLoading: true`로 두고 Firebase 세션 복원을 비동기로 처리하지만, `Home`은 `isLoggedIn`만 확인해 인증 초기화 완료 전 상태를 비회원으로 해석했습니다. 이 구간에서 홈 데이터 초기화와 위시리스트 요청도 비회원 상태 기준으로 시작될 수 있었습니다.

### 처리

- `Home`에서 인증 스토어의 `isLoading`을 `isAuthLoading`으로 받아 인증 상태가 확정될 때까지 공통 세션 복원 로딩 화면을 표시합니다.
- 인증 초기화 중에는 홈 데이터 초기화·위치 기반 조회와 위시리스트 초기화를 보류합니다.
- Header·Sidebar는 기존의 인증 로딩 스켈레톤을 유지해, 홈·Header·Sidebar가 같은 인증 상태 기준으로 렌더링됩니다.

### 확인 기준

- 로그인 상태에서 새로고침해도 비회원 홈이 먼저 노출되지 않고 세션 복원 로딩 뒤 회원 홈이 표시되어야 합니다.
- 실제 비로그인 사용자는 인증 초기화 완료 후 기존 비회원 홈을 정상적으로 확인할 수 있어야 합니다.
- 로그인·로그아웃과 Google OAuth 신규 가입·기존 계정 안내 흐름은 기존 동작을 유지해야 합니다.

## 2. Google-only 계정 비밀번호 변경 차단

### 문제

Google 계정으로 로그인한 사용자의 설정 화면에도 이메일·비밀번호 계정용 변경 폼이 표시됐습니다. 이 폼은 `EmailAuthProvider` 재인증을 사용하므로 Google 비밀번호를 입력해도 `auth/wrong-password` 오류가 발생해 사용자가 혼란스러울 수 있었습니다.

### 처리

- 설정 화면은 Firebase `providerData`에 `password` 제공업체가 연결된 경우에만 비밀번호 변경 폼을 표시합니다.
- Google-only 계정에는 Google 계정 보안 설정에서 비밀번호를 관리한다는 안내를 표시합니다.
- `authApi.updatePassword()`도 `password` 제공업체 연결 여부를 재확인해 UI를 우회한 호출을 차단합니다.
- Firebase의 비밀번호 변경 API는 Google 계정 비밀번호를 변경할 수 없습니다. 과거 변경 성공 사례가 있다면 해당 Firebase 사용자에 이메일·비밀번호 제공업체도 연결되어 있었고, 변경된 값은 그 Firebase 이메일·비밀번호 자격 증명입니다.

### 확인 기준

- Google-only 계정에서는 변경 입력 필드·버튼이 노출되지 않고 안내만 표시되어야 합니다.
- 이메일·비밀번호 계정과 `password` 제공업체가 연결된 복수 제공업체 계정은 현재 비밀번호 확인 후 변경할 수 있어야 합니다.

## 3. CodeRabbit 리뷰: 좋아요 UID 하위 규칙의 상위 쓰기 권한 우회 차단

### 문제

게시글·댓글 데이터의 상위 `.write` 규칙이 작성자에게 전체 콘텐츠 쓰기를 허용하고 있었습니다. Realtime Database Rules는 상위에서 허용된 `.write`를 하위 규칙이 취소할 수 없으므로, 콘텐츠 작성자는 `likeUserIds/{uid}`의 하위 규칙과 관계없이 다른 사용자의 좋아요 키 또는 전체 좋아요 맵을 변경할 수 있었습니다.

### 처리

- 좋아요 데이터를 콘텐츠 레코드에서 분리해 `likes/{콘텐츠유형}/{콘텐츠ID}/{uid}`에 저장하도록 변경했습니다.
- 콘텐츠 경로의 기존 `likeUserIds`는 검증 규칙으로 새 쓰기를 차단하고, 좋아요 변경은 분리된 경로에서 인증 사용자 자신의 UID에 대해서만 허용합니다.
- 기존 `likeUserIds` 데이터는 Admin SDK 스크립트로 분리 경로에 복사한 뒤 원본 필드를 정리합니다. 마이그레이션 완료 표식은 일반 사용자가 쓸 수 없습니다.
- `@firebase/rules-unit-testing`과 Realtime Database Emulator 기반 회귀 테스트를 추가해, 콘텐츠 작성자의 레거시 좋아요 맵 추가·변경과 타 사용자 분리 좋아요 키 변경은 거부되고 일반 사용자의 자기 키 토글은 허용되는지 검증합니다.

### 실행 방법

```powershell
npm run test:database-rules
```

Firebase Emulator가 자동으로 기동된 뒤 테스트가 종료되면 정리됩니다. 운영 반영은 아래 순서로 진행합니다.

```powershell
firebase deploy --only database
$env:GOOGLE_CLOUD_PROJECT = "newagent-9c2a8"
node functions/scripts/migrateLegacyLikeUserIds.js
node functions/scripts/migrateLegacyLikeUserIds.js --commit
firebase deploy --only hosting
```

`database` Rules를 먼저 배포해 기존 콘텐츠 내부 좋아요 변경을 멈춘 뒤 dry-run 결과를 확인하고 실제 변환을 실행합니다. 마지막으로 Hosting을 배포합니다. 이 순서에서는 Rules 배포와 Hosting 배포 사이에 기존 클라이언트의 좋아요 버튼이 잠시 거부될 수 있으므로 짧은 점검 시간에 진행합니다.

### 확인 기준

- 게시글·댓글 작성자가 콘텐츠 내부 `likeUserIds`를 추가·변경하거나, 분리된 경로에서 다른 사용자의 좋아요 키를 변경할 수 없어야 합니다.
- 로그인 사용자는 분리된 좋아요 경로에서 자신의 키를 추가·취소할 수 있어야 합니다.
- 기존 좋아요 수·내 계정의 좋아요 상태가 마이그레이션 후에도 유지되어야 합니다.

## 4. Google OAuth·좋아요 운영 점검 기록

### 수동 점검 결과

- Google-only 계정에서 비밀번호 변경 폼이 노출되지 않고 Google 계정 관리 안내가 표시되는 것을 확인했습니다.
- 신규·기존 Google 계정의 로그인과 회원가입 분기, 로그인·로그아웃, 게시글·게시글 댓글·여행지 댓글 좋아요의 추가·취소·누적 흐름이 정상 동작하는 것을 확인했습니다.
- 기존 Google 계정으로 회원가입을 재시도할 때 기존 계정 안내가 표시되고, 회원 홈으로 잘못 이동하지 않는 것을 확인했습니다.

### 배포 전 최종 확인

- 현재 브랜치의 인증 복원 깜빡임 보정과 Google-only 비밀번호 변경 차단은 커밋·배포 뒤 운영 URL에서 새로고침과 설정 화면을 한 번 더 확인합니다.
- Realtime Database Rules는 `firebase deploy --only database`로 반영된 상태를 유지하고, 배포 환경에서도 좋아요 권한과 수치가 일치하는지 확인합니다.
