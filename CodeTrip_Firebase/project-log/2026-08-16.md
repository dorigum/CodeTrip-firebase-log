Gemini API 호출 구조를 클라이언트 직접 호출에서 Firebase Callable Function 프록시 구조로 전환했습니다. 공개 Hosting 환경에서 Gemini API 키가 브라우저 번들에 포함될 수 있는 위험을 줄이고, 서버 측 Secret으로 키를 관리하는 방향으로 보안 구조를 개선했습니다.

## 11. 트러블슈팅

### 11.1 Firebase Functions Secret 등록과 배포에 Blaze 요금제가 필요한 문제

- **현상**: Gemini API 키를 Functions Secret으로 등록하고 `generateTripPlan` Callable Function을 배포하려는 과정에서 Firebase Functions 사용을 위해 Blaze 요금제 전환이 필요했습니다.
- **원인**: Spark 요금제에서는 이번 구조에서 필요한 Functions 배포와 Secret Manager 기반 비밀값 관리를 완료할 수 없었습니다. Gemini 호출을 서버 측으로 이전하려면 Firebase 프로젝트에 결제 계정 연결이 필요했습니다.
- **처리**:
  - Firebase 프로젝트 `newagent-9c2a8`을 Blaze 요금제로 전환했습니다.
  - 과금 방어를 위해 예산 알림을 설정했습니다.
  - `GEMINI_API_KEY`를 Functions Secret으로 등록했습니다.
  - `generateTripPlan` v2 Callable Function을 `asia-northeast3` 리전에 배포했습니다.
- **확인**:
  - `functions:list`에서 `generateTripPlan` Callable Function 배포 상태를 확인했습니다.
  - Hosting 재배포 후 미인증 요청 차단과 인증 smoke test를 확인했습니다.
- **운영 메모**:
  - Firebase 예산 알림과 Google AI Studio 선불 크레딧은 별도 체계입니다.
  - 제출 전에는 Firebase 사용량과 Gemini 사용량을 각각 확인해야 합니다.

### 11.2 Gemini 429 RESOURCE_EXHAUSTED와 AI Studio 크레딧 부족 문제

- **현상**: 새로 배포한 AI Planner에서 `generateTripPlan` 호출이 429로 실패하고, 사용자에게 “AI 여행 코스 생성 요청이 많습니다” 안내가 표시되었습니다.
- **원인**:
  - Callable Function 인증과 서버 호출 구조는 정상으로 확인되었습니다.
  - 직접 Gemini 최소 호출 결과 Google AI Studio 선불 크레딧 부족으로 `RESOURCE_EXHAUSTED`가 발생했습니다.
  - Firebase Blaze 예산과 AI Studio Gemini 크레딧은 서로 다른 결제·한도 체계였습니다.
- **처리**:
  - Google AI Studio에서 선불 크레딧을 충전했습니다.
  - 신규 Gemini API 키를 발급해 `.env`와 Firebase Secret version 2에 반영했습니다.
  - `generateTripPlan` Function을 재배포했습니다.
  - quota 보호를 위해 429 응답은 재시도하지 않고 사용자에게 대기 안내를 반환하는 방향으로 재시도 정책을 조정했습니다.
- **확인**:
  - Gemini 최소 호출이 200으로 응답했습니다.
  - 테스트 계정의 Firebase ID token 기반 Callable smoke test가 성공했습니다.
  - Functions 로그에서 `auth: VALID`, `Gemini trip plan generated` 흐름을 확인했습니다.
- **운영 메모**:
  - 429는 추가 재시도보다 사용량·크레딧 확인이 우선입니다.
  - 공개 시연 전에는 AI Studio 크레딧 잔액과 Gemini 사용량을 먼저 확인합니다.

### 11.3 Gemini API 키의 클라이언트 노출 가능성 제거

- **현상**: 기존 Gemini 호출 구조는 프론트엔드에서 직접 Gemini API를 호출할 수 있어, 공개 Firebase Hosting 배포 시 API 키가 브라우저 번들 또는 네트워크 요청 흐름에서 노출될 가능성이 있었습니다.
- **원인**: `VITE_` 환경변수는 Vite 빌드 과정에서 클라이언트 번들에 주입될 수 있으므로 비밀값 보호 수단이 아닙니다.
- **처리**:
  - `src/api/geminiApi.js`에서 브라우저 직접 Gemini 호출을 제거했습니다.
  - Firebase Callable Function `generateTripPlan`을 통해서만 Gemini 생성을 요청하도록 변경했습니다.
  - `GEMINI_API_KEY`를 Functions Secret으로 관리했습니다.
  - 신규 Gemini API 키를 Secret version 2로 등록하고 Function을 재배포했습니다.
  - 기존 노출 가능 키인 `Gemini API Key_temp`를 AI Studio에서 삭제했습니다.
- **확인**:
  - `dist` 산출물에서 Gemini API 키 원문이 발견되지 않았습니다.
  - 미인증 Callable 요청은 Gemini 호출 전에 401로 차단되었습니다.
  - 인증된 테스트 계정으로 AI 코스 생성 smoke test가 성공했습니다.
- **운영 메모**:
  - 현재 사용자별 호출 제한은 인스턴스 로컬 메모리 기반의 근사 제한입니다.
  - 전역 quota가 필요해지면 Firestore 또는 Realtime Database 기반 uid별 카운터로 이전해야 합니다.

### 11.4 카카오 지도 SDK 로딩 지연 시 상세 페이지가 무한 로딩처럼 보이는 문제

- **현상**: 여행지 또는 행사 상세 페이지에서 카카오 지도 영역이 계속 로딩되는 것처럼 보였습니다.
- **원인**:
  - Kakao SDK 응답 지연, 도메인·키 설정 문제, 네트워크 실패가 발생해도 사용자에게 별도 fallback 안내가 없었습니다.
  - 지도 중심 재조정 로직도 `window.kakao.maps` 준비 여부를 함께 확인하지 않았습니다.
  - 이후 로컬 확인에서 기존 `kakao-map-script` 태그가 이미 존재하지만 아직 로딩 중인 경우, 새 effect가 기존 script의 `load` 이벤트를 기다리지 못해 지연 fallback이 먼저 표시될 수 있음을 확인했습니다.
- **처리**:
  - Kakao SDK 로딩에 8초 timeout을 두고 fallback UI를 표시하도록 했습니다.
  - SDK 로드 실패와 API 키 누락 상태를 분리해 안내하도록 했습니다.
  - SDK URL을 `https://`로 고정했습니다.
  - 지도 객체 준비 전 resize 처리에서 Kakao 객체 존재 여부를 확인하도록 했습니다.
  - 기존 script 태그가 이미 있는 경우에도 `load`/`error` 이벤트 리스너를 등록하도록 보정했습니다.
  - 정상 로딩이 느린 환경을 고려해 SDK 대기 시간을 20초로 늘리고, timeout 직전 `window.kakao.maps` 준비 여부를 한 번 더 확인하도록 했습니다.
- **확인**:
  - `npm run lint`와 `npm run build`를 통과했습니다.
- **운영 메모**:
  - 배포 후에도 지도 fallback이 보이면 Kakao Developers의 JavaScript 키와 Web 플랫폼 도메인 등록 상태를 확인해야 합니다.

### 11.5 축제 목록 반응형 화면에서 마지막 줄 카드가 비는 문제

- **현상**: 데스크톱 3열 화면에서는 9개 기준으로 목록이 채워졌지만, 모바일에 가까운 2열 화면에서는 9개가 표시되어 마지막 줄이 1칸 비었습니다.
- **원인**: 페이지당 표시 개수가 고정값이었고, 실제 grid는 화면 폭에 따라 1열, 2열, 3열, 4열로 변경됐습니다.
- **처리**:
  - 화면 폭에 따라 페이지당 표시 개수를 계산하도록 변경했습니다.
  - 1280px 이상은 12개, 1024px 이상은 9개, 640px 이상은 10개, 640px 미만은 8개를 사용합니다.
  - resize 시 `requestAnimationFrame`으로 상태 변경을 제한했습니다.
- **확인**:
  - `npm run lint`와 `npm run build`를 통과했습니다.
- **운영 메모**:
  - 화면 폭 변경 시 페이지당 개수가 달라지므로 totalPages도 함께 재계산됩니다.

### 11.6 축제 API pool 호출량이 홈 미리보기 목적에 비해 과한 문제

- **현상**: Home에서는 축제 미리보기 3개만 필요하지만, 기존 축제 조회 함수는 목록 화면과 같은 큰 pool 정책을 공유했습니다.
- **원인**: 축제 API는 공공데이터 응답을 넓게 수집한 뒤 클라이언트에서 진행 중·예정 축제 필터링, 정렬, 페이지네이션을 수행하는 구조였습니다.
- **처리**:
  - 기본 축제 pool 상한을 3000건에서 1000건으로 낮췄습니다.
  - 호출자별로 `poolMaxRows`를 지정할 수 있도록 했습니다.
  - Home 트렌딩 축제 미리보기는 `poolMaxRows: 100`을 사용하도록 했습니다.
- **확인**:
  - `npm run lint`와 `npm run build`를 통과했습니다.
- **운영 메모**:
  - API 호출량을 더 줄이려면 Home 전용 endpoint wrapper와 축제 목록 전용 wrapper를 더 명확히 분리하는 방향을 검토합니다.

### 11.7 AI Planner 생성 버튼 연타로 Gemini 호출이 중복될 수 있는 문제

- **현상**: 생성 버튼에는 `disabled={generating}`가 있었지만, React 상태 반영 전 매우 빠른 연타가 들어오면 생성 함수가 중복 진입할 여지가 있었습니다.
- **원인**: UI disabled는 렌더 이후 적용되므로 이벤트 핸들러 진입 직후의 동기적 잠금 장치가 필요했습니다.
- **처리**:
  - `generationInFlightRef`를 추가해 `handleGenerate()` 진입 즉시 중복 실행을 차단했습니다.
  - `saveInFlightRef`를 추가해 AI 일정 저장도 중복 실행되지 않도록 했습니다.
  - 생성/저장 버튼에 `aria-busy`를 추가했습니다.
- **확인**:
  - `npm run lint`와 `npm run build`를 통과했습니다.
- **운영 메모**:
  - Gemini 비용 관리 관점에서 생성 버튼 중복 방지는 필수 게이트입니다.
