# CodeTrip 문서 작성 가이드

CodeTrip 프로젝트 문서를 같은 형식으로 유지하기 위한 작성 기준입니다. 작업 로그, 트러블슈팅, 실행/배포 가이드, 설계 문서가 서로 다른 위치에 흩어지지 않도록 아래 기준을 따릅니다.

## 1. 문서 폴더 구조

- `PROJECT_LOG.md`: 전체 작업 로그 목차와 날짜별 변경 요약을 관리합니다.
- `TROUBLESHOOTING.md`: 문제 해결 이력 색인입니다. 상세 내용은 날짜별 작업 로그에 작성하고, 이 문서에는 요약과 링크를 둡니다.
- `project-log/`: 날짜별 상세 작업 로그를 작성합니다.
- `project-log/archive/`: 기존 문서에서 분리한 원본, 이관본, 보존용 문서를 관리합니다.
- `guides/`: 실행, 배포, 문서 작성처럼 반복 참고가 필요한 가이드 문서를 관리합니다.
- `info/`: Firebase 상세 내역, Gemini 프롬프트 설계처럼 특정 기능이나 구조를 설명하는 참고 문서를 관리합니다.

## 2. 문서 작성 기본 원칙

CodeTrip 문서는 아래 원칙으로 작성합니다.

- `project-log/YYYY-MM-DD.md`: 실제 작업 내용, 판단 과정, 테스트 결과, 트러블슈팅 상세 원인을 가장 자세히 기록합니다.
- `PROJECT_LOG.md`: 날짜별 작업의 목차와 핵심 요약만 작성합니다.
- `TROUBLESHOOTING.md`: 문제 해결 이력의 색인으로 사용하며, 발생일, 영향 범위, 요약, 상세 로그 링크만 남깁니다.
- 같은 내용을 여러 문서에 길게 반복하지 않고, 상세 기록은 날짜별 로그 하나에 모읍니다.

## 3. 날짜별 작업 로그 작성 기준

날짜별 작업 로그 파일명은 `YYYY-MM-DD.md` 형식을 사용합니다.

예시:

```text
project-log/2026-07-25.md
```

작성 순서는 아래 흐름을 기본으로 합니다.

```md
# 2026-07-25 작업 로그

## 1. 작업 개요

오늘 진행한 작업의 전체 맥락을 요약합니다.

## 2. 주요 작업명

- 변경한 내용
- 수정한 파일 또는 기능
- 확인한 결과

## 3. 트러블슈팅 또는 추가 작업명

- 문제 원인
- 처리 방향
- 검증 결과
```

작업 로그에는 단순 결과만 적지 않고, 왜 수정했는지와 어떤 방향으로 결정했는지도 함께 남깁니다.

## 4. PROJECT_LOG.md 작성 기준

`PROJECT_LOG.md`는 전체 문서 목차와 날짜별 작업 요약만 관리합니다. 상세 구현 과정이나 긴 트러블슈팅 내용은 작성하지 않고, 해당 날짜 로그 파일로 연결합니다.

예시:

```md
- [2026-07-25](project-log/2026-07-25.md): CodeRabbit 리뷰 대응, 위시리스트 삭제 로직 보정, AI 코스 저장 검증 강화
```

요약은 한 줄을 기본으로 하되, 하루 작업 범위가 넓으면 쉼표로 주요 기능만 나열합니다.

## 5. 트러블슈팅 작성 기준

문제가 발생한 경우 상세 원인과 해결 과정은 해당 날짜의 `project-log/YYYY-MM-DD.md`에 작성합니다.

`TROUBLESHOOTING.md`에는 아래처럼 색인 형태로만 정리합니다.

```md
## 12. 문제 제목

- **발생일**: 2026-07-25
- **영향 범위**: 영향을 받은 기능 또는 화면
- **요약**: 문제의 핵심 원인과 처리 결과를 짧게 정리
- **상세 기록**: [2026-07-25 개발 로그](project-log/2026-07-25.md)의 관련 섹션 참고
```

트러블슈팅 번호는 기존 항목 다음 번호를 이어서 사용합니다. 중간에 참고 사항이나 보류 항목을 끼워 넣어 번호 흐름이 꼬이지 않도록 합니다.

## 6. 가이드 문서 작성 기준

실행 방법, 배포 방법, 문서 작성 규칙처럼 반복해서 참고해야 하는 내용은 `guides/` 하위에 작성합니다.

추천 파일명 예시:

```text
guides/Guide.md
guides/Project_Firebase_배포.md
guides/Document_Guide.md
```

가이드 문서는 특정 날짜의 작업 기록이 아니라 현재 기준의 최신 사용법을 설명합니다. 작업 과정은 날짜별 로그에, 최신 절차는 가이드 문서에 남깁니다.

## 7. 정보 문서 작성 기준

기능 설계, 데이터 구조, API 프롬프트처럼 프로젝트 이해를 돕는 참고 자료는 `info/` 하위에 작성합니다.

예시:

```text
info/Firebase_상세 내역서.md
info/Gemini_프롬프트_설계.md
```

정보 문서는 변경 이력 전체를 길게 나열하기보다 현재 구조와 결정 사항을 이해하기 쉽게 정리합니다.

## 8. 보류 작업 작성 기준

당장 진행하지 않지만 추후 반영해야 하는 작업은 날짜별 로그에 `보류 작업` 또는 `추후 개발 계획` 섹션으로 남깁니다.

예시:

```md
## 8. 보류 작업

- Firebase Functions 기반 Gemini API 호출 전환
- Gemini API key를 Functions Secret으로 관리
- 관광공사 좌표 기반 동선 정렬 고도화
```

보류 사유와 다시 시작할 조건을 같이 적으면 이후 작업 재개가 쉬워집니다.

## 9. 작성 시 주의사항

- 작업 내용은 날짜별 로그에 먼저 상세히 기록하고, `PROJECT_LOG.md`에는 해당 날짜 링크와 한 줄 요약만 추가합니다.
- 장애나 원인 분석이 포함된 내용은 날짜별 로그에 상세히 작성하고, `TROUBLESHOOTING.md`에는 요약과 해당 날짜 로그 링크만 연결합니다.
- 상세 내용이 긴 경우 `project-log/archive/`에 원본 또는 이관본을 분리하고, 본문에는 링크를 둡니다.
- `.obsidian`, `.claude`, `.claudian` 등 에디터 또는 AI 도구 설정 폴더는 프로젝트 문서 정리 대상에서 제외합니다.
- 문서 이동이나 파일명 변경 시 `PROJECT_LOG.md`, `TROUBLESHOOTING.md`의 링크도 함께 수정합니다.

## 10. 커밋 전 확인 기준

문서 작업 후에는 아래를 확인합니다.

```bash
git status --short
git diff --check
```

확인할 항목:

- 링크가 깨지지 않았는지
- 날짜별 로그 번호가 순서대로 이어지는지
- 트러블슈팅 번호가 중복되거나 건너뛰지 않았는지
- 의도하지 않은 `.obsidian` 또는 도구 설정 파일 변경이 포함되지 않았는지
